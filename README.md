# FightScore — запуск демо

Система управления соревнованиями по единоборствам: турниры, спортсмены, поединки, судейская панель и ТВ-табло с синхронизацией через WebSocket. Работает в локальной сети без интернета.

Документы: [ТЗ](docs/PROJECT_SPEC.md) · [архитектура](docs/ARCHITECTURE.md) · [схема БД](docs/DATABASE.md) · [план](docs/IMPLEMENTATION_PLAN.md).

> **Правила в демо условны.** Профиль «ДЕМО: очковый профиль» не является регламентом какой-либо федерации. Он помечен как демонстрационный в интерфейсе и на табло.

## Требования

- Node.js 24 LTS (≥ 24.15) или новее; проверено на 25.2.1.
- PostgreSQL ≥ 15, запущенный на этом компьютере (проверено на 18).

## Быстрый старт демо (рекомендуется)

Одна команда поднимает всё на этом компьютере: постоянную локальную PostgreSQL (`%LOCALAPPDATA%\FightScore\pgdemo`, порт `127.0.0.1:54330`, вход по паролю), backend (`:3001`) и frontend (`:3000`). Всё слушает только `127.0.0.1`. Supabase, `backend/.env` и системная служба PostgreSQL не затрагиваются. Команды для Git Bash, из корня репозитория:

```bash
cd backend && npm ci && cd ../frontend && npm ci && cd ..
```

```bash
bash scripts/demo.sh init
```

```bash
bash scripts/demo.sh start
```

```bash
bash scripts/demo.sh status
```

```bash
bash scripts/demo.sh stop
```

```bash
bash scripts/demo.sh rebuild
```

- `init` — однократная настройка: пароли БД и демо-пользователей в `backend/.env.demo` (игнорируется git, сохраняются первыми), кластер, базы `fightscore_demo` и `fightscore_test`, сборка, миграции, демо-данные. Повторный запуск безопасен: готовое окружение не меняется, прерванная настройка продолжается с сохранёнными паролем и данными. Если состояние неоднозначно (например, есть кластер, но нет файла с паролем), `init` ничего не меняет и объясняет, как восстановиться. Данные скрипт никогда не удаляет сам.
- Вход в демо: `demo.organizer`, `demo.chief`, `demo.judge`, пароль — `DEMO_PASSWORD` в `backend/.env.demo`. Если демо создано до появления этого ключа, пароль остаётся в `backend/.env`. `init` подсказывает, где он. Пароль задаётся один раз при создании пользователей: если поменять его в файле позже, пароль уже созданных пользователей не изменится.
- `start` запускает БД, backend и frontend в фоне, логи — в `%LOCALAPPDATA%\FightScore\run`. Перед запуском проверяет, что подключается именно к своему кластеру и базе. Если порт 3000, 3001 или 54330 занят другим процессом, этот компонент не запускается и команда завершается с ошибкой. Предупреждает, если сборка старше исходников.
- Порт 3000 занят (например, `npm run dev`): остановите тот процесс сами или запустите демо на другом порту — `FS_DEMO_WEB_PORT=3100 bash scripts/demo.sh start` и откройте http://localhost:3100. Порт запоминается: `status` и `stop` работают без переменной, вернуться на 3000 — `stop`, затем `FS_DEMO_WEB_PORT=3000 bash scripts/demo.sh start`. Для своего процесса backend демо получает `PUBLIC_ORIGINS` с этим портом и с 3000 (`backend/.env` не меняется). Сменить порт при запущенном backend нельзя: сначала `stop`. Учтите: dev-сервер на 3000 тоже обращается к backend демо на 3001, то есть к демо-базе.
- `npm run dev` во frontend всегда запускается на порту 3000 и падает с ошибкой, если порт занят: раньше Next.js молча переезжал на 3001 и занимал порт backend. Чтобы выбрать другой порт: `npm run dev -- -p 3002`. В режиме `dev-http` backend принимает запросы с любого адреса этого компьютера (`localhost`, `127.0.0.1`, `[::1]`, любой порт). Адреса из локальной сети по-прежнему перечисляются в `PUBLIC_ORIGINS`.
- `npm run dev` запускает только экраны. Перед стартом он проверяет backend и предупреждает, если тот не запущен. Для показа и презентации запускайте всё одной командой `bash scripts/demo.sh start`: это собранная версия без мигания стилей при первой загрузке. Если backend ещё запускается или перезапускается, страницы до 45 секунд ждут его с плашкой «Подключаемся к серверу…», а не показывают ошибку.
- Вход действует 7 дней (`SESSION_TTL_HOURS=168`). Сессию завершают кнопка «Выйти» и смена пароля.
- `stop` останавливает только процессы этого демо: они распознаются по командной строке с путями этого репозитория. Чужие процессы на тех же портах не трогаются, о них выводится предупреждение. Данные сохраняются.
- `status` показывает каждый компонент и возвращает код 1, если что-то не запущено, не отвечает или порт занят чужим процессом.
- `rebuild` пересобирает backend и frontend; выполняется при остановленном демо (`stop`, `rebuild`, `start`).
- Процессы, запущенные предыдущей версией скрипта, распознаются как чужие: остановите их один раз вручную.
- Переопределения: `PG_BIN` (путь к PostgreSQL, по умолчанию `/c/Program Files/PostgreSQL/18/bin`), `FS_DEMO_DIR`, `FS_DEMO_PGPORT`, `FS_DEMO_ENV` — отдельный кластер и файл пароля для тестов. Порты 3000 и 3001 общие: `start`/`stop` с этими переменными работают с backend и frontend основного демо.

Разделы 1–2 ниже описывают ручную установку на базу под системным пользователем PostgreSQL.

## 1. База данных (один раз, ручной вариант)

```bash
cd backend
npm ci
npm run db:setup
```

`db:setup` создаёт `backend/.env` со случайным паролем роли БД и запускает `psql` от имени суперпользователя `postgres`. Пароль `postgres` вводите сами, он нигде не сохраняется. Скрипт создаёт роль `fightscore` и базы `fightscore` и `fightscore_test`. Если `psql` лежит не в `C:\Program Files\PostgreSQL\18\bin`, укажите путь в переменной `PSQL`.

```bash
npm run db:migrate
npm run seed:demo
```

`seed:demo` создаёт демо-турнир, 8 спортсменов, 4 поединка, табло и пользователей `demo.organizer`, `demo.chief`, `demo.judge`. Их общий пароль — значение `DEMO_PASSWORD` в `backend/.env`. Администратора платформы (один на систему: блокирует и удаляет аккаунты, видит журнал) создаёт или сбрасывает команда `npm run admin:reset` в `backend`: она печатает логин и новый пароль один раз. Вход — ссылка «Вход для администратора» на странице входа (`/admin/login`). Подробности — `docs/ARCHITECTURE.md` §5.5.

## 2. Запуск

Backend (порт 3001):

```bash
cd backend
npm run build
npm run start:prod
```

Frontend (порт 3000), в другом терминале:

```bash
cd frontend
npm ci
npm run build
npm start
```

Откройте http://localhost:3000 — стартовая страница с тремя входами: «Организатор», «Судья», «Табло». Организатор может зарегистрироваться сам (флаг `ALLOW_REGISTRATION`, по умолчанию включён в режиме `dev-http`), обзор — `/dashboard`.

Установка как приложение (PWA): в Chrome/Edge на `localhost` или по HTTPS появится предложение «Установить»; на iPhone — «Поделиться» → «На экран „Домой“». Без связи с сервером приложение не работает, показывается заглушка.

## 3. Сценарий демонстрации

1. Войдите как `demo.organizer`. На странице «Турниры» откройте «Демо-турнир FightScore»: там участники и поединки. Создайте турнир, спортсмена или поединок, чтобы проверить управление.
2. В разделе «Табло» нажмите «Открыть табло» у «Татами 1 — ТВ». Это публичная страница без входа: откройте её на втором экране или ТВ и нажмите «На весь экран».
3. В другом браузере (или окне инкогнито) откройте главную → «Судья» → войдите как `demo.chief` → «Судить» у поединка №1.
4. «Начать поединок» → «Старт». Начисляйте баллы, ставьте паузу, записывайте нарушения. Табло обновляется сразу, без перезагрузки.
5. Войдите как `demo.judge` в третьем окне: судья может начислять баллы и нарушения, но не управляет таймером и не завершает поединок (так задано профилем).
6. Отмените ошибочное действие в журнале: исходная запись остаётся с пометкой об отмене.
7. «Завершить поединок» → «Подтвердить результат». Результат сохраняется в БД и появляется на табло и на обзоре.
8. Остановите демо командой `bash scripts/demo.sh stop`, не закрывая открытые страницы: судейская панель и табло покажут потерю связи. После `bash scripts/demo.sh start` данные и запущенный таймер восстановятся. Если backend запущен вручную (раздел 2), остановите его Ctrl+C в его окне.

## 4. Работа в локальной сети

1. В `backend/.env`: `HOST=<IP сервера в сети>`, `PUBLIC_ORIGINS=http://<IP>:3000`.
2. Frontend: `npx next start -H <IP>`.
3. На ноутбуке судьи и на ТВ откройте `http://<IP>:3000`.

Режим `DEPLOY_MODE=dev-http` передаёт данные **без шифрования**. Он допустим только в доверенной изолированной сети и **не подходит для реального турнира** (см. [ARCHITECTURE.md §9.1](docs/ARCHITECTURE.md)). HTTPS-развёртывание — этап 8.

Если backend работает не на `127.0.0.1:3001`, задайте `BACKEND_INTERNAL_URL` **до** `npm run build` во frontend (адрес встраивается в правила прокси при сборке), а для WebSocket — `NEXT_PUBLIC_REALTIME_URL`.

## 5. Почему не Supabase для живого демо

Каждое обращение к БД в Сингапуре стоит ~250–320 мс сети (сами запросы выполняются быстрее 0,5 мс), поэтому экраны открываются за 0,5–1 с, а команда судьи доходит до табло примерно за 1 с (оценка). На локальной БД — 10–40 мс. Замеры: `docs/ARCHITECTURE.md` §18.

## 6. Проверки

```bash
cd backend
npm run lint
npm test          # unit: движок правил, конфигурация, health
set -a; . ./.env.demo; set +a; npm run test:e2e   # база fightscore_test из scripts/demo.sh
```

`test:e2e` пересоздаёт схему базы из `TEST_DATABASE_URL`. Тест запускается, только если имя базы оканчивается на `_test`, хост локальный (`127.0.0.1`, `localhost` или `::1`) и база не совпадает с базой из `DATABASE_URL`. Перед сбросом схемы он дополнительно сверяет имя базы с `current_database()`. В остальных случаях, в том числе на Supabase и рабочей базе, тесты пропускаются: в итоге будет `skipped`.

```bash
cd ../frontend
npm run lint
npm run build
```
