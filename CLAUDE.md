# FightScore

Система управления соревнованиями по единоборствам: турниры, спортсмены, судьи, поединки, счёт, таймер, результаты. Судья ведёт поединок на ноутбуке, зрители видят счёт и таймер на ТВ-табло. Должна работать в локальной сети без интернета.

Полное ТЗ: [docs/PROJECT_SPEC.md](docs/PROJECT_SPEC.md). Читать нужный раздел перед работой над соответствующей функцией.

## Структура репозитория

Один git-репозиторий в корне `FightScore/` (ветка `master`, remote нет). История шаблона frontend сохранена: смотреть через `git log --follow frontend/<файл>`.

- `frontend/` — Next.js 16 (App Router), React 19, TypeScript.
- `backend/` — NestJS, TypeScript, тесты на Vitest, линтер oxlint.
- `docs/` — ТЗ и архитектурные решения.

## Frontend: куда класть компоненты

Маршруты Next.js живут в `frontend/src/app/` (`page.tsx`, `layout.tsx`). Файлы маршрутов остаются тонкими и рендерят компоненты из `frontend/src/components/`:

- `components/pages/` — полные страницы сайта (одна страница = один компонент, его импортирует соответствующий `app/**/page.tsx`).
- `components/widgets/` — отдельные крупные секции страниц (например, блок активных турниров на обзоре, таблица поединков).
- `components/ui/` — мелкие переиспользуемые блоки вёрстки: кнопки, поля, карточки, бейджи, диалоги.
- `components/layout/` — каркас приложения: хедер, футер, сайдбар.

- `src/lib/` — не-UI код: API-клиент, realtime-клиент, сессия, форматирование, типы ответов API.

Стили — SCSS Modules рядом с компонентом, общие токены — в `src/app/globals.scss`, миксины — в `src/styles/`. Tailwind не используется.

Запуск демо, проверки и работа в LAN описаны в `README.md`. Отличия MVP от полной архитектуры — `docs/ARCHITECTURE.md` §16.

## Next.js

В `frontend/AGENTS.md` действует правило: эта версия Next.js отличается от знакомой по обучению. Перед написанием frontend-кода читать актуальную документацию в `frontend/node_modules/next/dist/docs/` и учитывать предупреждения об устаревших API.

## Обязательные ограничения

- Сервер — единственный источник достоверного состояния поединка. Бизнес-правила и проверка прав — только на сервере, не в React-компонентах. Состояние поединка не хранить только в браузере.
- Таймер считается по серверным временным меткам. Команды изменения имеют идентификаторы (защита от повторов) и проверку версии состояния.
- Каждое подтверждённое действие пишется в журнал. Исправления добавляют записи, а не стирают историю.
- К поединку привязывается неизменяемая версия профиля правил.
- Не придумывать спортивные правила. Демонстрационные профили явно помечать как демонстрационные.
- Локальная работа без интернета: никаких внешних API, CDN-шрифтов и иконок для проведения поединка. Google OAuth — только дополнительно к локальным аккаунтам.
- Если сервер или сеть недоступны, интерфейс явно показывает ошибку и не выдаёт устаревшие данные за актуальные.
- Не добавлять ORM, state management, UI-библиотеки и другие крупные зависимости без обоснования.
- Не хранить секреты и реальные пароли в репозитории и клиентском коде.

## Процесс

- Работа идёт по этапам из раздела 19 ТЗ. Следующий этап начинается после проверки предыдущего.
- Сначала изучать существующий код, не переписывать рабочие части без причины, не удалять функции без согласования.
- Не заявлять о прохождении тестов без запуска. Не скрывать ошибки типов, линтера и сборки.
- Массовые изменения — только после плана.
- Архитектурные решения документировать в `docs/`.
