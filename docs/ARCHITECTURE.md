## 2. Общая схема

```
 Ноутбук судьи      Ноутбук организатора      ТВ-компьютер (киоск)
   (браузер/PWA)        (браузер/PWA)            /display/<token>
        │                     │                         │
        └──────── локальная сеть (LAN), без интернета ──┘
                              │
                 Сервер соревнований (один компьютер)
          ┌───────────────────┴───────────────────┐
          │ Next.js (next start)   :3000           │  UI, SSR, rewrite /api/* → backend
          │ NestJS                 :3001           │  REST /api, Socket.IO /realtime, /public
          │ PostgreSQL             :5432 (localhost)│  единственное постоянное хранилище
          └────────────────────────────────────────┘
```

- **Модульный монолит.** Один процесс NestJS, один процесс Next.js, одна БД. Без микросервисов, брокеров, Redis.
- **Один процесс backend — сознательное решение.** Рассылка изменений в реальном времени идёт внутри процесса, поэтому Redis-адаптер не нужен. Горизонтальное масштабирование ТЗ не требует; если потребуется, точка расширения — адаптер Socket.IO (§6.6).
- **Сервер — единственный источник истины** для состояния поединка (ТЗ §5). Frontend показывает подтверждённое сервером состояние и отправляет команды. Спортивную логику во frontend не дублируем.

## 4. Модули backend

### 4.1. Ответственность

| Модуль | Отвечает за | Таблицы |
|---|---|---|
| **Database** (инфраструктура) | Пул `pg`, `withTransaction()`, раннер миграций. | `schema_migrations` |
| **Audit** | Запись в журнал административных действий (append-only) и чтение журнала. | `audit_log` |
| **Access** (Roles/Permissions) | Каталог ролей и прав, назначения ролей с областью (система/турнир), `PermissionService.can(user, permission, scope)`. | `roles`, `role_permissions`, `user_role_assignments` |
| **Users** | Учётные записи, активация/деактивация, привязка Google-идентичности. | `users`, `user_identities` |
| **Auth** | Вход по паролю, Google OAuth, сессии, выход, `AuthGuard` (HTTP) и аутентификация WS-рукопожатия. | `sessions` |
| **Disciplines** | Справочник дисциплин. | `disciplines` |
| **Rules** | Профили правил, версии, жизненный цикл draft → approved → archived, схема определения, **движок правил** (чистые функции). | `rule_profiles`, `rule_profile_versions` |
| **Athletes** | Спортсмены, страны и флаги, клубы. | `athletes`, `countries`, `clubs` |

| **Officials** | Назначение главного судьи и судей, их права в поединке. | `match_officials` |
| **Scoring** | **Конвейер команд поединка**: авторизация, идемпотентность, версия, движок правил, таймер, журнал событий, фиксация результата. | `match_states`, `match_events`, `match_results` (запись) |
| **Displays** | Публичные табло: токен, привязка к поединку, публичная проекция состояния. | `displays` |

Страны и клубы входят в Athletes, категории — в Tournaments: отдельные модули ради справочников были бы преждевременным дроблением. Публичная регистрация, сетки, площадки — будущие модули (ТЗ §3.2), сейчас не создаются.

### 4.2. Граф зависимостей (без циклов)

```
Database ◄── все модули
Audit       → Database
Access      → Database
Users       → Access, Audit
Auth        → Users, Access
Disciplines → Access, Audit
Rules       → Disciplines, Access, Audit
Athletes    → Access, Audit
Tournaments → Athletes, Disciplines, Rules, Access, Audit
Matches     → Tournaments, Rules, Access, Audit
Officials   → Matches, Users, Access, Audit
Scoring     → Matches, Officials, Rules, Access, Audit
Displays    → Matches, Scoring (чтение снимка), Access, Audit
Realtime    → Scoring, Displays, Auth
```

Ключевые правила:

- **Scoring не знает о Realtime.** Scoring после коммита транзакции публикует `MatchStateChanged` в собственный поток (RxJS `Subject`, rxjs уже в зависимостях). Realtime подписывается. Так нет цикла Scoring ↔ Realtime, а Scoring тестируется без сокетов.
- **Access не знает об Officials.** Права в рамках поединка проверяет Scoring/Officials, комбинируя `Access` (роль в турнире) и `match_officials` (назначение на поединок).
- Модуль экспортирует только сервис-фасад; репозитории (SQL) — внутренние.

### 4.3. Внутреннее устройство модуля

```
modules/scoring/
├── scoring.module.ts
├── scoring.controller.ts     # HTTP: POST /api/matches/:id/commands, GET /api/matches/:id/state
├── scoring.service.ts        # конвейер команд (§6.2)
├── scoring.repository.ts     # SQL, только через переданный клиент транзакции
├── timer.ts                  # чистые функции расчёта времени
└── *.spec.ts
```

- **SQL без ORM.** Параметризованные запросы через `pg`. Репозиторий принимает `PoolClient`, чтобы сервис управлял транзакцией.
- **Валидация входа.** Схемы zod из `packages/contracts` + собственный `ZodValidationPipe` (≈20 строк). `class-validator` не добавляем: иначе схемы пришлось бы дублировать для frontend.
- **Ошибки.** Единый формат `{ code, message, details? }`. Коды (`FORBIDDEN`, `VERSION_CONFLICT`, `RULE_VIOLATION`, `INVALID_TRANSITION`, …) объявлены в contracts.

## 5. Авторизация и права

### 5.1. Аутентификация

- **Локальные аккаунты** (обязательны, работают без интернета). Хеш пароля — `scrypt` из `node:crypto` с солью и параметрами в строке хеша. Нативная зависимость (argon2) не нужна, Windows-сборка не ломается.
- **Сессии на сервере, не JWT.** Случайный токен 32 байта → httpOnly-cookie `fs_session`. В БД хранится только SHA-256 токена. Отзыв мгновенный (выход, деактивация пользователя), это проще и безопаснее JWT для локального сервера. Скользящее продление, абсолютный срок жизни задаётся конфигурацией.
- **Google OAuth** — authorization code flow с PKCE, **только для входа в уже существующего** пользователя: Google-идентичность привязывается к локальному аккаунту. Самостоятельной регистрации через Google нет. Без интернета кнопка Google скрыта или неактивна, локальный вход работает. Требования к HTTPS и redirect URI — §9.1.
- **Первый владелец** создаётся CLI-скриптом `backend/scripts/create-owner` на сервере (пароль вводится интерактивно), не через публичный эндпоинт и не через демо-секреты (ТЗ §16.5).

### 5.2. Модель прав

- **Права — коды** (`tournament.manage`, `athlete.manage`, `match.create`, `official.assign`, `rules.approve`, `display.operate`, `audit.read`, `system.manage`, …), перечислены в contracts.
- **Роли** (`owner`, `organizer`, `chief_judge`, `judge`, `display_operator`) — наборы прав в `role_permissions`, наполняются миграцией.
- **Назначение роли** имеет область: `system` или `tournament` (ТЗ §7 — «ограничения на уровне системы, турнира, площадки и поединка»). Область «площадка» зарезервирована до появления площадок (ТЗ §3.2). Уровень «поединок» — это `match_officials`.
- **«Зритель» — не аккаунт.** Это отсутствие аутентификации. Ему доступны только публичные маршруты табло.
- **Права судьи в поединке** = назначение в `match_officials` (роль `chief_judge`/`judge` + список разрешённых действий) **∩** действия, разрешённые профилем правил для этой роли. Профиль может сузить права, назначение не может расширить их сверх профиля.

### 5.3. Где проверяется

| Канал | Механизм |
|---|---|
| HTTP | `AuthGuard` (сессия) → `PermissionGuard` с декоратором `@RequirePermission(code, scopeResolver)`. `scopeResolver` достаёт `tournamentId` из параметров или из сущности. Запрет доступа к чужим турнирам — следствие области назначения. |
| WebSocket `/realtime` | Сессия проверяется при рукопожатии (cookie). Каждая подписка и **каждая команда** проходят ту же проверку прав, что и HTTP (общий `PermissionService`). |
| WebSocket `/public` | Без сессии. Доступ по токену табло, только чтение публичной проекции. Команды не принимаются. |
| Next.js `proxy.ts` | Только оптимистичный редирект на `/login` при отсутствии cookie. **Не** является проверкой прав (так рекомендует документация Next.js 16: `middleware` переименован в `proxy`). |

### 5.4. CSRF, XSS, частота запросов

- Cookie сессии: `HttpOnly`, `SameSite=Strict`, `Path=/`. В рабочем развёртывании — `Secure` и имя с префиксом `__Host-` (§9.1).
- Мутирующие HTTP-запросы: проверка заголовка `Origin` по allowlist + обязательный заголовок `X-FightScore-Request: 1` (простой формой не отправить).
- WS-рукопожатие: проверка `Origin` по тому же allowlist.
- XSS: React экранирует вывод; `dangerouslySetInnerHTML` запрещён; CSP-заголовки задаются в Next.js на этапе 8.
- Ограничение частоты: вход и OAuth-callback — обязательно; команды поединка — мягкий лимит на соединение.

## 6. Поединок: состояние, команды, таймер

### 6.1. Жизненный цикл

ТЗ §11 даёт примерный список состояний, где «пауза» стоит рядом с «идёт». Разделяем **статус поединка** и **статус таймера**, иначе пауза таймера внутри раунда и перерыв между раундами смешаются:

```
matches.status:  prepared → ready → live → awaiting_confirmation → completed
                     │         │      │              │
                     └─────────┴──────┴──────────────┴──► cancelled   (только до completed)

match_states.timer_status (только при status = live):  stopped ⇄ running
```

- `prepared` — поединок создан, данные можно править. `ready` — участники, судьи и версия правил зафиксированы, ждём старта.
- «Пауза» из ТЗ = `live` + таймер `stopped`. Если регламенту нужны отдельные фазы (перерыв, медицинский тайм-аут), они задаются профилем как фазы внутри `live`, а не новыми статусами ядра.
- Переходы выполняют только команды Scoring. Прямой `PATCH status` не существует.

### 6.2. Конвейер команды

Все изменения поединка — HTTP или WS — проходят один путь `ScoringService.execute(command, actor)`:

```
command = { commandId: uuid (генерирует клиент), matchId, expectedVersion, type, payload }

BEGIN
 1. SELECT … FROM match_states WHERE match_id = $1 FOR UPDATE      -- сериализация команд поединка
 2. есть match_events с (match_id, command_id)?  → вернуть прежний результат (duplicate), COMMIT
 3. проверить права актора (Access + match_officials + профиль правил)
 4. проверить expectedVersion (§6.3)
 5. engine.apply(ruleVersion.definition, state, command, serverNow) → новое состояние | RULE_VIOLATION
 6. INSERT match_events (seq = version + 1, …)
 7. UPDATE match_states SET …, version = version + 1
 8. при завершении: INSERT match_results, UPDATE matches.status
COMMIT
 9. publish MatchStateChanged → Realtime рассылает подписчикам
```

- Шаг 9 строго **после** коммита: клиент никогда не видит неподтверждённое состояние.
- Ответ на команду (`ack`): `accepted | duplicate | rejected` + новая версия или код ошибки.
- Уникальный индекс `(match_id, command_id)` — вторая линия защиты от повторов, даже при гонке.

### 6.3. Конфликты версий

Строгое совпадение `expectedVersion` для всех команд ломает работу нескольких судей: два судьи одновременно начисляют баллы, второй получает ложный конфликт. Поэтому движок классифицирует типы команд:

- **Накопительные** (начисление/снятие балла, запись предупреждения): применяются к актуальному состоянию даже при устаревшей `expectedVersion`. Потери нет: их сериализует блокировка строки (шаг 1).
- **Зависящие от состояния** (запуск/остановка/установка таймера, смена периода, исправление события, завершение, подтверждение результата): требуют `expectedVersion == version`, иначе `VERSION_CONFLICT` + свежий снимок. Клиент **не повторяет такую команду автоматически**: решение снова принимает человек.

### 6.4. Исправления

Отмена ошибочного действия — новая команда `void_event { targetEventId, reason }`. Она создаёт событие с `corrects_event_id`. Исходное событие не удаляется и не меняется (ТЗ §11). Новое состояние пересчитывается **воспроизведением** журнала без аннулированных событий. Тот же механизм используется в тесте «состояние = свёртка журнала».

### 6.5. Таймер

Хранится в `match_states`: `timer_status`, `timer_remaining_ms`, `timer_started_at` (серверное время), `period_index`, `version`.

- **Старт:** `timer_started_at = now()` (время сервера БД внутри транзакции), `running`. Повторный старт запущенного таймера → `INVALID_TRANSITION`.
- **Пауза:** `remaining = max(0, remaining − (now − started_at))`, `stopped`.
- **Текущее значение** вычисляется, а не тикает в базе: `remaining − (now − started_at)`.
- **Истечение:** Scoring держит в памяти `setTimeout` на момент истечения для каждого запущенного таймера. По срабатыванию выполняется системная команда `timer_expired` (через тот же конвейер, актор `system`). При старте процесса таймеры восстанавливаются из `match_states`; если время истекло, пока сервер был выключен, `timer_expired` выполняется сразу с фиксацией фактического времени.
- **Корректировка времени** — отдельная команда с причиной, пишется в журнал. Допустимые пределы задаёт профиль.
- **Клиенты** получают `serverTime` в каждом снимке и событии, оценивают смещение часов (с поправкой на RTT по ping) и рисуют отсчёт через `requestAnimationFrame`. Сверка — при каждом событии и периодически (~10 с).
- Значения длительности и количества периодов берутся **только** из профиля правил. В коде их нет.
- Точность официально не гарантируется до измерений на реальном оборудовании (ТЗ §12). План измерений — этап 9.

### 6.6. Realtime-протокол

**Библиотека:** Socket.IO (`@nestjs/websockets` + `@nestjs/platform-socket.io` на сервере, `socket.io-client` на клиенте). Обоснование: комнаты (поединок = комната), подтверждения (ack) для команд, автоматическое переподключение и heartbeat из коробки. На голом `ws` всё это пришлось бы писать вручную. Работает полностью в LAN. Совместимость с NestJS 12 проверяется при установке на этапе 7.

| Направление | Сообщение | Назначение |
|---|---|---|
| C→S | `match.subscribe {matchId}` | Подписка (проверка прав) → ответ `match.snapshot`. |
| S→C | `match.snapshot {state, version, serverTime}` | Полное подтверждённое состояние. |
| C→S | `match.command {commandId, matchId, expectedVersion, type, payload}` + ack | Команда изменения → ack `{status, version, error?}`. |
| S→C | `match.event {version, event, state, serverTime}` | Подтверждённое изменение. |
| C→S | `match.resync {matchId}` | Запрос снимка. |
| S→C | `error {code, message}` | Ошибка протокола или прав. |
| `/public` C→S | `display.subscribe {token}` | Табло → `display.snapshot` с **публичной проекцией**. |

**Восстановление после разрыва:** при каждом подключении клиент заново подписывается и получает снимок. Если пришло событие с `version ≠ последняя + 1`, клиент запрашивает `resync`. Неподтверждённые команды хранятся в памяти вкладки с исходным `commandId` и после переподключения отправляются повторно. Сервер вернёт `duplicate`, если команда уже применена.

**Индикатор связи** (ТЗ §8.8): `connected` / `reconnecting` / `offline`. При `reconnecting`/`offline` судейская панель блокирует ввод команд и помечает показания как «последние подтверждённые, связь потеряна». Устаревшее не выдаётся за актуальное (ТЗ §6). Табло при потере связи показывает явную плашку.

**Подключение к WS.** HTTP-запросы браузера идут на тот же origin через rewrite Next.js `/api/* → backend`. Socket.IO подключается к backend напрямую (`<тот же хост>:3001`). Cookie не изолируются по порту, поэтому сессия передаётся. Origin проверяется allowlist. Если на этапе 7 подтвердится, что rewrite Next.js корректно проксирует WebSocket upgrade, можно перейти на единый origin. Это проверяется, а не предполагается.

## 7. Профили правил и движок

- **Профиль** (`rule_profiles`) — именованная линия правил дисциплины. **Версия** (`rule_profile_versions`) содержит `definition` (JSONB), источник (название документа, редакция, URL/файл, дата), дату вступления в силу, статус.
- **Неизменяемость:** после `approved` поля определения и источника заблокированы триггером БД. Разрешён только переход `approved → archived`. Поединок ссылается на конкретную версию (FK). Новая редакция = новая версия, старые поединки не меняются (ТЗ §10).
- **Утверждение** требует права `rules.approve`. Для неdemo-версии обязателен источник. Демо-версии имеют `is_demo = true`, видимую пометку в UI и на табло. Утвердить их как официальные нельзя (ограничение БД).
- **Схема `definition`** (zod в contracts) описывает *параметры*, а не код: периоды и длительности, типы действий начисления/снятия с величинами, типы предупреждений и штрафов, их последствия, способы завершения, права ролей судей, пределы корректировки времени, публичные поля табло.
- **Движок** — набор чистых функций `apply(definition, state, command, now)` в модуле Rules. Ключ `engine` в версии выбирает обработчик (`generic-points@1` и будущие специфичные). Это и есть расширяемость ТЗ §10: дисциплине с особой логикой (например, автоматические последствия штрафов) добавляется свой обработчик. Ядро и существующие обработчики не переписываются. Версия обработчика фиксируется в версии профиля, поэтому старые поединки воспроизводятся старой логикой.
- **В коде нет ни одного спортивного значения.** До получения регламентов существуют только демо-профили в тестовых фикстурах и seed для разработки.

`page.tsx` остаются тонкими и рендерят `components/pages/*` (соглашение `CLAUDE.md`).

### 8.2. Данные

- **Чтение:** серверные компоненты обращаются к backend по внутреннему адресу (`BACKEND_INTERNAL_URL`) и пробрасывают cookie сессии. С `cacheComponents: true` данные динамические по умолчанию: не кэшируем ничего, связанное с поединком и правами. `use cache` допустим только для справочников без персональных данных (страны).
- **Мутации:** клиентские компоненты → `fetch('/api/…')` (rewrite на backend). Server Actions для мутаций **не используем**, чтобы у системы была одна поверхность API с одной авторизацией.
- **Живые экраны** (судейская панель, табло) — клиентские компоненты на `src/lib/realtime`. Начальный снимок приходит по WS, а не из SSR, чтобы не было рассинхрона версий.
- **State management:** React state + контекст для соединения. Библиотеки не добавляем (ТЗ §4).

### 8.3. Судейская панель и табло

- Панель строится из `definition` версии правил и снимка: кнопки = действия, разрешённые профилем этой роли судьи. Сервер всё равно проверяет каждую команду. Опасные действия (завершение, исправление, сброс времени) подтверждаются отдельным шагом. Неподтверждённая команда видна как «отправлено, ждёт сервера».
- Табло — отдельная компоновка под большой экран, только публичная проекция. Без cookie, без административной навигации.

### 8.4. PWA

- `app/manifest.ts` (встроенная конвенция Next.js 16) + собственный минимальный service worker, который кэширует **только статическую оболочку и ассеты**. Ответы API и WS не кэшируются, иначе нарушится запрет показывать устаревшее как актуальное.
- **Ограничение:** service worker и установка PWA работают только в secure context (HTTPS или `localhost`). На ноутбуке судьи, открывающем `http://192.168.x.x:3000`, PWA не установится. Поэтому установка PWA в LAN возможна только в рабочем развёртывании с HTTPS (§9.1).

## 9. Локальный режим, развёртывание, резервные копии

- **Базовый вариант — нативная установка без Docker:** PostgreSQL (официальный установщик), Node.js LTS, `npm ci`, `npm run build`, запуск двух процессов. Docker на машине не установлен, а ТЗ допускает Docker Compose «если подходит окружению». Docker Compose можно добавить позже как альтернативу, но не сейчас (ADR на этапе 8).
- **Сетевые интерфейсы:** PostgreSQL слушает только `localhost`. Backend и frontend слушают адрес из конфигурации (`HOST`). По умолчанию `127.0.0.1`, LAN-адрес задаётся явно при развёртывании. Сервер не открывается всем интерфейсам по умолчанию (ТЗ §15).
- **Ресурсы:** шрифты (`next/font/local`), иконки и флаги лежат в репозитории. Во время работы нет обращений к CDN.
- **Секреты:** `.env` вне репозитория, в репозитории `.env.example` без реальных значений. Backend при старте проверяет конфигурацию (zod) и отказывается стартовать в `production` с демо-значениями.
- **Резервная копия:** `pg_dump -Fc` скриптом `backend/scripts/backup` в каталог с датой. Восстановление `pg_restore` в чистую БД — документированная и **проверяемая** процедура (этап 8). Перед каждой миграцией в production — обязательная копия.
- **Перезапуск:** всё подтверждённое лежит в PostgreSQL. После старта backend восстанавливает таймеры (§6.5), клиенты переподключаются и получают снимки.
- **Телеметрия:** на сервере соревнований не должно быть фоновых обращений во внешние сервисы: `@nestjs/observe` удаляется (§14), для Next.js задаётся `NEXT_TELEMETRY_DISABLED=1`.

### 9.1. Режимы развёртывания и HTTPS (решение владельца, 2026-10-16)

Два режима. Режим задаётся конфигурацией backend и frontend (`DEPLOY_MODE`) и проверяется при старте.

| | `dev-http` — разработка и стендовые проверки | `production` — рабочее развёртывание на турнире |
|---|---|---|
| Транспорт | HTTP, в том числе по LAN-адресу | **Только HTTPS** (и `wss://` для WebSocket) |
| Где допустим | `localhost` или **доверенная изолированная сеть** без посторонних устройств | Любая сеть турнира |
| Cookie сессии | `fs_session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, **без** `Secure` | `__Host-fs_session`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, без `Domain` |
| PWA | Только с `localhost` | Да (secure context) |
| Google OAuth | Только с `localhost` (для отладки) | Только при выполнении условий ниже |
| Локальный вход | Да | Да, всегда |

**HTTP не является безопасным режимом для реального турнира.** В `dev-http` токен сессии и пароли идут по сети открытым текстом: любое устройство в той же сети может их перехватить и выдать себя за судью. Поэтому:

- `production` без HTTPS **не стартует**: backend проверяет, что публичный origin (`PUBLIC_ORIGIN`) начинается с `https://`, а сертификат и ключ доступны.
- `dev-http` выводит в лог предупреждение при каждом старте. Интерфейс показывает постоянную плашку «Тестовый режим без шифрования».
- Документация развёртывания (этап 8) не описывает проведение турнира в `dev-http`.

**Требования к рабочему HTTPS:**

- TLS-сертификат выпускается **локальным центром сертификации** организатора. Корневой сертификат CA один раз устанавливается на устройства турнира (ноутбуки судей, ТВ-компьютер). Это работает без интернета. Самоподписанный сертификат с ручным «принять риск» на каждом устройстве не допускается: такая привычка делает перехват незаметным.
- Сертификат выдаётся на имя хоста сервера и/или его фиксированный LAN-IP. Закрытые ключи CA и сервера хранятся вне репозитория, доступ — только у администратора сервера.
- `next start` не поддерживает HTTPS: в документации Next.js 16 флаг `--experimental-https` есть только у `next dev`. Поэтому TLS завершается перед приложениями. Способ — открытый вопрос (§11.2, п. Б).
- Заголовок `Strict-Transport-Security` включается в `production`.

**Google OAuth:**

- Работает только при одновременном выполнении трёх условий: есть доступ в интернет, есть HTTPS и redirect URI, зарегистрированный в Google Cloud Console. По правилам Google redirect URI должен быть `https` с доменным именем; IP-адреса запрещены, исключение — `localhost`. Это проверяется при настройке на этапе 8.
- Следствие: для OAuth нужно доменное имя, указывающее на сервер турнира. Без него OAuth в LAN недоступен, и это допустимо.
- `client_secret` хранится только в конфигурации backend (`.env` вне репозитория), во frontend не передаётся.
- Если интернета нет, backend не пытается обращаться к Google: кнопка входа через Google скрыта, показывается понятное сообщение.

**Локальный вход при отсутствии интернета:**

- Локальная учётная запись (логин + пароль, `scrypt`) — основной и всегда доступный способ входа.
- Каждый, кто работает на турнире (организатор, судьи, оператор табло), **обязан иметь локальный пароль**. Аккаунт только с Google (`password_hash IS NULL`) нельзя назначить судьёй поединка. Интерфейс назначения предупреждает об этом заранее.
- Сброс пароля без интернета выполняет владелец или организатор через интерфейс либо CLI на сервере. Восстановления по e-mail нет.

### 11.3. Принятые по умолчанию решения по ТЗ

1. **«Зритель» как роль** (ТЗ §7.6) и **«Role» как сущность** (ТЗ §9): зритель — неаутентифицированный доступ к публичным маршрутам, в `roles` его нет.

4. **Пересмотр подтверждённого результата:** в v1 `match_results` неизменяем. Будущая процедура — новая запись «пересмотр» со ссылкой на исходную.

6. **Несколько категорий у спортсмена в турнире:** разрешено (уникальность `(tournament, athlete, category)`).
