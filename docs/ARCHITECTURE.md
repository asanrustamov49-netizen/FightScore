## 2. Общая схема

```
 Ноутбук судьи      Ноутбук организатора      ТВ-компьютер (киоск)
   (браузер/PWA)        (браузер/PWA)            /display/<token>
        │                     │                         │
        └──────── локальная сеть (LAN), без интернета ──┘
                              │
                 Сервер соревнований (один компьютер)
          ┌───────────────────┴───────────────────┐
          │ Next.js (next start)   :3000           │  UI, SSR, rewrite /api/* → backend
          │ NestJS                 :3001           │  REST /api, Socket.IO /realtime, /public
          │ PostgreSQL             :5432 (localhost)│  единственное постоянное хранилище
          └────────────────────────────────────────┘
```

Схема выше — **автономный локальный** вариант для турниров. Кроме него есть **облачный** вариант (Vercel + Render + PostgreSQL) для публичного стенда и удалённого доступа — §9.2. Код приложения один и тот же, различается конфигурация.

- **Модульный монолит.** Один процесс NestJS, один процесс Next.js, одна БД. Без микросервисов, брокеров, Redis.
- **Один процесс backend — сознательное решение.** Рассылка изменений в реальном времени идёт внутри процесса, поэтому Redis-адаптер не нужен. Горизонтальное масштабирование ТЗ не требует; если потребуется, точка расширения — адаптер Socket.IO (§6.6).
- **Сервер — единственный источник истины** для состояния поединка (ТЗ §5). Frontend показывает подтверждённое сервером состояние и отправляет команды. Спортивную логику во frontend не дублируем.

## 4. Модули backend

### 4.1. Ответственность

| Модуль | Отвечает за | Таблицы |
|---|---|---|
| **Database** (инфраструктура) | Пул `pg`, `withTransaction()`, раннер миграций. | `schema_migrations` |
| **Audit** | Запись в журнал административных действий (append-only) и чтение журнала. | `audit_log` |
| **Access** (Roles/Permissions) | Каталог ролей и прав, назначения ролей с областью (система/турнир), `PermissionService.can(user, permission, scope)`. | `roles`, `role_permissions`, `user_role_assignments` |
| **Users** | Учётные записи, активация/деактивация, привязка Google-идентичности. | `users`, `user_identities` |
| **Auth** | Вход по паролю, Google OAuth, сессии, выход, `AuthGuard` (HTTP) и аутентификация WS-рукопожатия. | `sessions` |
| **Disciplines** | Справочник дисциплин. | `disciplines` |
| **Rules** | Профили правил, версии, жизненный цикл draft → approved → archived, схема определения, **движок правил** (чистые функции). | `rule_profiles`, `rule_profile_versions` |
| **Athletes** | Спортсмены, страны и флаги, клубы. | `athletes`, `countries`, `clubs` |

| **Officials** | Назначение главного судьи и судей, их права в поединке. | `match_officials` |
| **Scoring** | **Конвейер команд поединка**: авторизация, идемпотентность, версия, движок правил, таймер, журнал событий, фиксация результата. | `match_states`, `match_events`, `match_results` (запись) |

Страны и клубы входят в Athletes, категории — в Tournaments: отдельные модули ради справочников были бы преждевременным дроблением. Публичная регистрация, сетки, площадки — будущие модули (ТЗ §3.2), сейчас не создаются.

### 4.2. Граф зависимостей (без циклов)

```
Database ◄── все модули
Audit       → Database
Access      → Database
Users       → Access, Audit
Auth        → Users, Access
Disciplines → Access, Audit
Rules       → Disciplines, Access, Audit
Athletes    → Access, Audit
Tournaments → Athletes, Disciplines, Rules, Access, Audit
Matches     → Tournaments, Rules, Access, Audit
Officials   → Matches, Users, Access, Audit
Scoring     → Matches, Officials, Rules, Access, Audit
Displays    → Matches, Scoring (чтение снимка), Access, Audit
Realtime    → Scoring, Displays, Auth
```

Ключевые правила:

- **Scoring не знает о Realtime.** Scoring после коммита транзакции публикует `MatchStateChanged` в собственный поток (RxJS `Subject`, rxjs уже в зависимостях). Realtime подписывается. Так нет цикла Scoring ↔ Realtime, а Scoring тестируется без сокетов.
- **Access не знает об Officials.** Права в рамках поединка проверяет Scoring/Officials, комбинируя `Access` (роль в турнире) и `match_officials` (назначение на поединок).
- Модуль экспортирует только сервис-фасад; репозитории (SQL) — внутренние.

### 4.3. Внутреннее устройство модуля

```
modules/scoring/
├── scoring.module.ts
├── scoring.controller.ts     # HTTP: POST /api/matches/:id/commands, GET /api/matches/:id/state
├── scoring.service.ts        # конвейер команд (§6.2)
├── scoring.repository.ts     # SQL, только через переданный клиент транзакции
├── timer.ts                  # чистые функции расчёта времени
└── *.spec.ts
```

- **SQL без ORM.** Параметризованные запросы через `pg`. Репозиторий принимает `PoolClient`, чтобы сервис управлял транзакцией.
- **Валидация входа.** Схемы zod из `packages/contracts` + собственный `ZodValidationPipe` (≈20 строк). `class-validator` не добавляем: иначе схемы пришлось бы дублировать для frontend.
- **Ошибки.** Единый формат `{ code, message, details? }`. Коды (`FORBIDDEN`, `VERSION_CONFLICT`, `RULE_VIOLATION`, `INVALID_TRANSITION`, …) объявлены в contracts.

## 5. Авторизация и права

### 5.1. Аутентификация

- **Локальные аккаунты** (обязательны, работают без интернета). Хеш пароля — `scrypt` из `node:crypto` с солью и параметрами в строке хеша. Нативная зависимость (argon2) не нужна, Windows-сборка не ломается.
- **Сессии на сервере, не JWT.** Случайный токен 32 байта → httpOnly-cookie `fs_session`. В БД хранится только SHA-256 токена. Отзыв мгновенный (выход, деактивация пользователя), это проще и безопаснее JWT для локального сервера. Скользящее продление, абсолютный срок жизни задаётся конфигурацией.
- **Google OAuth** — authorization code flow с PKCE, **только для входа в уже существующего** пользователя: Google-идентичность привязывается к локальному аккаунту. Самостоятельной регистрации через Google нет. Без интернета кнопка Google скрыта или неактивна, локальный вход работает. Требования к HTTPS и redirect URI — §9.1.
- **Первый владелец** создаётся CLI-скриптом `backend/scripts/create-owner` на сервере (пароль вводится интерактивно), не через публичный эндпоинт и не через демо-секреты (ТЗ §16.5).

### 5.2. Модель прав

- **Права — коды** (`tournament.manage`, `athlete.manage`, `match.create`, `official.assign`, `rules.approve`, `display.operate`, `audit.read`, `system.manage`, …), перечислены в contracts.
- **Роли** (`owner`, `organizer`, `chief_judge`, `judge`, `display_operator`) — наборы прав в `role_permissions`, наполняются миграцией.
- **Назначение роли** имеет область: `system` или `tournament` (ТЗ §7 — «ограничения на уровне системы, турнира, площадки и поединка»). Область «площадка» зарезервирована до появления площадок (ТЗ §3.2). Уровень «поединок» — это `match_officials`.
- **«Зритель» — не аккаунт.** Это отсутствие аутентификации. Ему доступны только публичные маршруты табло.
- **Права судьи в поединке** = назначение в `match_officials` (роль `chief_judge`/`judge` + список разрешённых действий) **∩** действия, разрешённые профилем правил для этой роли. Профиль может сузить права, назначение не может расширить их сверх профиля.

### 5.3. Где проверяется

| Канал | Механизм |
|---|---|
| HTTP | `AuthGuard` (сессия) → `PermissionGuard` с декоратором `@RequirePermission(code, scopeResolver)`. `scopeResolver` достаёт `tournamentId` из параметров или из сущности. Запрет доступа к чужим турнирам — следствие области назначения. |
| WebSocket `/realtime` | Сессия проверяется при рукопожатии (cookie или одноразовый билет — §9.2, вопрос Ж). Каждая подписка и **каждая команда** проходят ту же проверку прав, что и HTTP (общий `PermissionService`). |
| WebSocket `/public` | Без сессии. Доступ по токену табло, только чтение публичной проекции. Команды не принимаются. |
| Next.js `proxy.ts` | Только оптимистичный редирект на `/login` при отсутствии cookie. **Не** является проверкой прав (так рекомендует документация Next.js 16: `middleware` переименован в `proxy`). |

### 5.4. CSRF, XSS, частота запросов

- Cookie сессии: `HttpOnly`, `SameSite=Strict`, `Path=/`. В рабочем развёртывании — `Secure` и имя с префиксом `__Host-` (§9.1).
- Мутирующие HTTP-запросы: проверка заголовка `Origin` по allowlist + обязательный заголовок `X-FightScore-Request: 1` (простой формой не отправить).
- WS-рукопожатие: проверка `Origin` по тому же allowlist.
- XSS: React экранирует вывод; `dangerouslySetInnerHTML` запрещён; CSP-заголовки задаются в Next.js на этапе 8.
- Ограничение частоты: вход и OAuth-callback — обязательно; команды поединка — мягкий лимит на соединение.

## 6. Поединок: состояние, команды, таймер

### 6.1. Жизненный цикл

ТЗ §11 даёт примерный список состояний, где «пауза» стоит рядом с «идёт». Разделяем **статус поединка** и **статус таймера**, иначе пауза таймера внутри раунда и перерыв между раундами смешаются:

```
matches.status:  prepared → ready → live → awaiting_confirmation → completed
                     │         │      │              │
                     └─────────┴──────┴──────────────┴──► cancelled   (только до completed)

match_states.timer_status (только при status = live):  stopped ⇄ running
```

- `prepared` — поединок создан, данные можно править. `ready` — участники, судьи и версия правил зафиксированы, ждём старта.
- «Пауза» из ТЗ = `live` + таймер `stopped`. Если регламенту нужны отдельные фазы (перерыв, медицинский тайм-аут), они задаются профилем как фазы внутри `live`, а не новыми статусами ядра.
- Переходы выполняют только команды Scoring. Прямой `PATCH status` не существует.

### 6.2. Конвейер команды

Все изменения поединка — HTTP или WS — проходят один путь `ScoringService.execute(command, actor)`:

```
command = { commandId: uuid (генерирует клиент), matchId, expectedVersion, type, payload }

BEGIN
 1. SELECT … FROM match_states WHERE match_id = $1 FOR UPDATE      -- сериализация команд поединка
 2. есть match_events с (match_id, command_id)?  → вернуть прежний результат (duplicate), COMMIT
 3. проверить права актора (Access + match_officials + профиль правил)
 4. проверить expectedVersion (§6.3)
 5. engine.apply(ruleVersion.definition, state, command, serverNow) → новое состояние | RULE_VIOLATION
 6. INSERT match_events (seq = version + 1, …)
 7. UPDATE match_states SET …, version = version + 1
 8. при завершении: INSERT match_results, UPDATE matches.status
COMMIT
 9. publish MatchStateChanged → Realtime рассылает подписчикам
```

- Шаг 9 строго **после** коммита: клиент никогда не видит неподтверждённое состояние.
- Ответ на команду (`ack`): `accepted | duplicate | rejected` + новая версия или код ошибки.
- Уникальный индекс `(match_id, command_id)` — вторая линия защиты от повторов, даже при гонке.

### 6.3. Конфликты версий

Строгое совпадение `expectedVersion` для всех команд ломает работу нескольких судей: два судьи одновременно начисляют баллы, второй получает ложный конфликт. Поэтому движок классифицирует типы команд:

- **Накопительные** (начисление/снятие балла, запись предупреждения): применяются к актуальному состоянию даже при устаревшей `expectedVersion`. Потери нет: их сериализует блокировка строки (шаг 1).
- **Зависящие от состояния** (запуск/остановка/установка таймера, смена периода, исправление события, завершение, подтверждение результата): требуют `expectedVersion == version`, иначе `VERSION_CONFLICT` + свежий снимок. Клиент **не повторяет такую команду автоматически**: решение снова принимает человек.

Отклик панели судьи (2026-10-22). При удалённой БД (Supabase) команда подтверждается за 0,5–1 с. Чтобы судья не ждал, панель сразу рисует **превью** результата своей команды: очки ± баллы действия, таймер на паузе или запущен. Превью живёт только на экране этого судьи и снимается, когда приходит снимок сервера с версией этой команды; при отказе сервера оно убирается, и экран возвращается к подтверждённому состоянию. Табло и журнал показывают только подтверждённые данные. Зависящая от состояния команда уходит после ответа на предыдущие команды этого судьи, а её `expectedVersion` учитывает версии из этих ответов: «+3» и сразу «Пауза» не дают ложного конфликта. Пул соединений с БД держит 3 соединения открытыми (пинг раз в 20 с), чтобы команда после паузы в работе не ждала нового подключения (~2 с до Supabase).

Дисквалификация (2026-10-23). Способ завершения «Дисквалификация соперника» (код `dq`, с победителем) доступен в любом профиле правил: если профиль сам не содержит способа дисквалификации, он добавляется при загрузке определения (`withDisqualification`). Сохранённая версия профиля не меняется. Судья завершает поединок кнопкой «Дисквалификация» в углу нарушителя, победа уходит сопернику. На табло у дисквалифицированного угла показывается 0 и надпись «Дисквалифицирован» уже с момента завершения (до подтверждения); баллы в состоянии и журнале сохраняются.

### 6.4. Исправления

Отмена ошибочного действия — новая команда `void_event { targetEventId, reason }`. Она создаёт событие с `corrects_event_id`. Исходное событие не удаляется и не меняется (ТЗ §11). Новое состояние пересчитывается **воспроизведением** журнала без аннулированных событий. Тот же механизм используется в тесте «состояние = свёртка журнала».

### 6.5. Таймер

Хранится в `match_states`: `timer_status`, `timer_remaining_ms`, `timer_started_at` (серверное время), `period_index`, `version`.

- **Старт:** `timer_started_at = now()` (время сервера БД внутри транзакции), `running`. Повторный старт запущенного таймера → `INVALID_TRANSITION`.
- **Пауза:** `remaining = max(0, remaining − (now − started_at))`, `stopped`.
- **Текущее значение** вычисляется, а не тикает в базе: `remaining − (now − started_at)`.
- **Истечение:** Scoring держит в памяти `setTimeout` на момент истечения для каждого запущенного таймера. По срабатыванию выполняется системная команда `timer_expired` (через тот же конвейер, актор `system`). При старте процесса таймеры восстанавливаются из `match_states`; если время истекло, пока сервер был выключен, `timer_expired` выполняется сразу с фиксацией фактического времени.
- **Корректировка времени** — отдельная команда с причиной, пишется в журнал. Допустимые пределы задаёт профиль.
- **Клиенты** получают `serverTime` в каждом снимке и событии, оценивают смещение часов (с поправкой на RTT по ping) и рисуют отсчёт через `requestAnimationFrame`. Сверка — при каждом событии и периодически (~10 с).
- Значения длительности и количества периодов берутся **только** из профиля правил. В коде их нет.
- Точность официально не гарантируется до измерений на реальном оборудовании (ТЗ §12). План измерений — этап 9.

### 6.6. Realtime-протокол

**Библиотека:** Socket.IO (`@nestjs/websockets` + `@nestjs/platform-socket.io` на сервере, `socket.io-client` на клиенте). Обоснование: комнаты (поединок = комната), подтверждения (ack) для команд, автоматическое переподключение и heartbeat из коробки. На голом `ws` всё это пришлось бы писать вручную. Работает полностью в LAN. Совместимость с NestJS 12 проверяется при установке на этапе 7.

| Направление | Сообщение | Назначение |
|---|---|---|
| C→S | `match.subscribe {matchId}` | Подписка (проверка прав) → ответ `match.snapshot`. |
| S→C | `match.snapshot {state, version, serverTime}` | Полное подтверждённое состояние. |
| C→S | `match.command {commandId, matchId, expectedVersion, type, payload}` + ack | Команда изменения → ack `{status, version, error?}`. |
| S→C | `match.event {version, event, state, serverTime}` | Подтверждённое изменение. |
| C→S | `match.resync {matchId}` | Запрос снимка. |
| S→C | `error {code, message}` | Ошибка протокола или прав. |
| `/public` C→S | `display.subscribe {token}` | Табло → `display.snapshot` с **публичной проекцией**. |

**Восстановление после разрыва:** при каждом подключении клиент заново подписывается и получает снимок. Если пришло событие с `version ≠ последняя + 1`, клиент запрашивает `resync`. Неподтверждённые команды хранятся в памяти вкладки с исходным `commandId` и после переподключения отправляются повторно. Сервер вернёт `duplicate`, если команда уже применена.

**Индикатор связи** (ТЗ §8.8): `connected` / `reconnecting` / `offline`. При `reconnecting`/`offline` судейская панель блокирует ввод команд и помечает показания как «последние подтверждённые, связь потеряна». Устаревшее не выдаётся за актуальное (ТЗ §6). Табло при потере связи показывает явную плашку.

**Подключение к WS.** HTTP-запросы браузера идут на тот же origin через rewrite Next.js `/api/* → backend`. Socket.IO подключается к backend напрямую (`<тот же хост>:3001`). Cookie не изолируются по порту, поэтому сессия передаётся. Origin проверяется allowlist. Если на этапе 7 подтвердится, что rewrite Next.js корректно проксирует WebSocket upgrade, можно перейти на единый origin. Это проверяется, а не предполагается. В облачном варианте backend на другом домене, и cookie в рукопожатие не попадёт — там нужен одноразовый билет (§9.2).

## 7. Профили правил и движок

- **Профиль** (`rule_profiles`) — именованная линия правил дисциплины. **Версия** (`rule_profile_versions`) содержит `definition` (JSONB), источник (название документа, редакция, URL/файл, дата), дату вступления в силу, статус.
- **Неизменяемость:** после `approved` поля определения и источника заблокированы триггером БД. Разрешён только переход `approved → archived`. Поединок ссылается на конкретную версию (FK). Новая редакция = новая версия, старые поединки не меняются (ТЗ §10).
- **Утверждение** требует права `rules.approve`. Для неdemo-версии обязателен источник. Демо-версии имеют `is_demo = true`, видимую пометку в UI и на табло. Утвердить их как официальные нельзя (ограничение БД).
- **Схема `definition`** (zod в contracts) описывает *параметры*, а не код: периоды и длительности, типы действий начисления/снятия с величинами, типы предупреждений и штрафов, их последствия, способы завершения, права ролей судей, пределы корректировки времени, публичные поля табло.
- **Движок** — набор чистых функций `apply(definition, state, command, now)` в модуле Rules. Ключ `engine` в версии выбирает обработчик (`generic-points@1` и будущие специфичные). Это и есть расширяемость ТЗ §10: дисциплине с особой логикой (например, автоматические последствия штрафов) добавляется свой обработчик. Ядро и существующие обработчики не переписываются. Версия обработчика фиксируется в версии профиля, поэтому старые поединки воспроизводятся старой логикой.
- **В коде нет ни одного спортивного значения.** До получения регламентов существуют только демо-профили в тестовых фикстурах и seed для разработки.

```
├── (auth)/login/page.tsx

│   ├── page.tsx                       # обзор

```

`page.tsx` остаются тонкими и рендерят `components/pages/*` (соглашение `CLAUDE.md`).

### 8.2. Данные

- **Чтение:** серверные компоненты обращаются к backend по внутреннему адресу (`BACKEND_INTERNAL_URL`) и пробрасывают cookie сессии. С `cacheComponents: true` данные динамические по умолчанию: не кэшируем ничего, связанное с поединком и правами. `use cache` допустим только для справочников без персональных данных (страны).
- **Мутации:** клиентские компоненты → `fetch('/api/…')` (rewrite на backend). Server Actions для мутаций **не используем**, чтобы у системы была одна поверхность API с одной авторизацией.
- **Живые экраны** (судейская панель, табло) — клиентские компоненты на `src/lib/realtime`. Начальный снимок приходит по WS, а не из SSR, чтобы не было рассинхрона версий.
- **State management:** React state + контекст для соединения. Библиотеки не добавляем (ТЗ §4).

### 8.3. Судейская панель и табло

- Панель строится из `definition` версии правил и снимка: кнопки = действия, разрешённые профилем этой роли судьи. Сервер всё равно проверяет каждую команду. Опасные действия (завершение, исправление, сброс времени) подтверждаются отдельным шагом. Неподтверждённая команда видна как «отправлено, ждёт сервера».
- Табло — отдельная компоновка под большой экран, только публичная проекция. Без cookie, без административной навигации.

### 8.4. PWA

- `app/manifest.ts` (встроенная конвенция Next.js 16) + собственный минимальный service worker, который кэширует **только статическую оболочку и ассеты**. Ответы API и WS не кэшируются, иначе нарушится запрет показывать устаревшее как актуальное.
- **Ограничение:** service worker и установка PWA работают только в secure context (HTTPS или `localhost`). На ноутбуке судьи, открывающем `http://192.168.x.x:3000`, PWA не установится. Поэтому установка PWA в LAN возможна только в рабочем развёртывании с HTTPS (§9.1).

## 9. Локальный режим, развёртывание, резервные копии

- **Базовый вариант — нативная установка без Docker:** PostgreSQL (официальный установщик), Node.js LTS, `npm ci`, `npm run build`, запуск двух процессов. Docker на машине не установлен, а ТЗ допускает Docker Compose «если подходит окружению». Docker Compose можно добавить позже как альтернативу, но не сейчас (ADR на этапе 8).
- **Сетевые интерфейсы:** PostgreSQL слушает только `localhost`. Backend и frontend слушают адрес из конфигурации (`HOST`). По умолчанию `127.0.0.1`, LAN-адрес задаётся явно при развёртывании. Сервер не открывается всем интерфейсам по умолчанию (ТЗ §15). Значения для всех вариантов — §9.3.
- **Ресурсы:** шрифты (`next/font/local`), иконки и флаги лежат в репозитории. Во время работы нет обращений к CDN.
- **Секреты:** `.env` вне репозитория, в репозитории `.env.example` без реальных значений. Backend при старте проверяет конфигурацию (zod) и отказывается стартовать в `production` с демо-значениями.
- **Резервная копия:** `pg_dump -Fc` скриптом `backend/scripts/backup` в каталог с датой. Восстановление `pg_restore` в чистую БД — документированная и **проверяемая** процедура (этап 8). Перед каждой миграцией в production — обязательная копия.
- **Перезапуск:** всё подтверждённое лежит в PostgreSQL. После старта backend восстанавливает таймеры (§6.5), клиенты переподключаются и получают снимки.
- **Телеметрия:** на сервере соревнований не должно быть фоновых обращений во внешние сервисы: `@nestjs/observe` удалён (§14), для Next.js задаётся `NEXT_TELEMETRY_DISABLED=1`.

### 9.1. Режимы развёртывания и HTTPS (решение владельца, 2026-10-16)

Два режима безопасности. Режим задаётся конфигурацией backend и frontend (`DEPLOY_MODE`) и проверяется при старте. Режим не зависит от варианта размещения (§9.2): `production` — любое рабочее развёртывание, локальное или облачное. Облачный вариант всегда работает в `production`.

| | `dev-http` — разработка и стендовые проверки | `production` — рабочее развёртывание на турнире |
|---|---|---|
| Транспорт | HTTP, в том числе по LAN-адресу | **Только HTTPS** (и `wss://` для WebSocket) |
| Где допустим | `localhost` или **доверенная изолированная сеть** без посторонних устройств | Любая сеть турнира |
| Cookie сессии | `fs_session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, **без** `Secure` | `__Host-fs_session`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, без `Domain` |
| PWA | Только с `localhost` | Да (secure context) |
| Google OAuth | Только с `localhost` (для отладки) | Только при выполнении условий ниже |
| Локальный вход | Да | Да, всегда |

**HTTP не является безопасным режимом для реального турнира.** В `dev-http` токен сессии и пароли идут по сети открытым текстом: любое устройство в той же сети может их перехватить и выдать себя за судью. Поэтому:

- `production` без HTTPS **не стартует**: backend проверяет, что публичный origin (`PUBLIC_ORIGIN`) начинается с `https://`, а сертификат и ключ доступны.
- `dev-http` выводит в лог предупреждение при каждом старте. Интерфейс показывает постоянную плашку «Тестовый режим без шифрования».
- Документация развёртывания (этап 8) не описывает проведение турнира в `dev-http`.

**Требования к рабочему HTTPS:**

- TLS-сертификат выпускается **локальным центром сертификации** организатора. Корневой сертификат CA один раз устанавливается на устройства турнира (ноутбуки судей, ТВ-компьютер). Это работает без интернета. Самоподписанный сертификат с ручным «принять риск» на каждом устройстве не допускается: такая привычка делает перехват незаметным.
- Сертификат выдаётся на имя хоста сервера и/или его фиксированный LAN-IP. Закрытые ключи CA и сервера хранятся вне репозитория, доступ — только у администратора сервера.
- `next start` не поддерживает HTTPS: в документации Next.js 16 флаг `--experimental-https` есть только у `next dev`. Поэтому TLS завершается перед приложениями. Способ — открытый вопрос (§11.2, п. Б).
- Заголовок `Strict-Transport-Security` включается в `production`.

**Google OAuth:**

- Работает только при одновременном выполнении трёх условий: есть доступ в интернет, есть HTTPS и redirect URI, зарегистрированный в Google Cloud Console. По правилам Google redirect URI должен быть `https` с доменным именем; IP-адреса запрещены, исключение — `localhost`. Это проверяется при настройке на этапе 8.
- Следствие: для OAuth нужно доменное имя, указывающее на сервер турнира. Без него OAuth в LAN недоступен, и это допустимо.
- `client_secret` хранится только в конфигурации backend (`.env` вне репозитория), во frontend не передаётся.
- Если интернета нет, backend не пытается обращаться к Google: кнопка входа через Google скрыта, показывается понятное сообщение.

**Локальный вход при отсутствии интернета:**

- Локальная учётная запись (логин + пароль, `scrypt`) — основной и всегда доступный способ входа.
- Каждый, кто работает на турнире (организатор, судьи, оператор табло), **обязан иметь локальный пароль**. Аккаунт только с Google (`password_hash IS NULL`) нельзя назначить судьёй поединка. Интерфейс назначения предупреждает об этом заранее.
- Сброс пароля без интернета выполняет владелец или организатор через интерфейс либо CLI на сервере. Восстановления по e-mail нет.

### 9.2. Варианты размещения: локальный и облачный (решение владельца, 2026-10-16)

Один код, два варианта размещения. Вариант задаётся конфигурацией (`DEPLOY_TARGET=local | cloud`).

| | **Автономный локальный** (`local`) | **Облачный** (`cloud`) |
|---|---|---|
| Назначение | Проведение турниров, в том числе без интернета | Публичный стенд (демонстрация) и удалённый доступ |
| Frontend | `next start` на сервере соревнований | **Vercel** |
| Backend | NestJS на сервере соревнований | **Render** (Web Service) |
| БД | Локальная PostgreSQL на том же компьютере | Управляемая PostgreSQL (провайдер — открытый вопрос З) |
| Интернет | Не нужен | Нужен всем клиентам |
| HTTPS | Локальный CA (§9.1), в `dev-http` — без шифрования | TLS платформ Vercel и Render |
| Google OAuth | Только при выполнении условий §9.1 | Доступен (есть домен и HTTPS) |
| Резервные копии | `pg_dump` скриптом (§9) | Средства провайдера БД + периодический `pg_dump` |

**Данные двух вариантов независимы.** Это две отдельные базы, у каждой свои пользователи, турниры и результаты. Автоматической синхронизации между локальным сервером и облаком **нет и не обещается**. Перенос результатов турнира в облако (экспорт/импорт или односторонняя публикация) — отдельная будущая задача (ТЗ §3.2: экспорт результатов, удалённый мониторинг). Её нужно спроектировать отдельно: идентификаторы, конфликты, права, целостность журнала.

**Особенности облачного варианта:**

- **Один origin для браузера.** Браузер обращается только к домену Vercel. Next.js проксирует `/api/*` на Render через rewrite, как и в локальном варианте (§8.2). Поэтому cookie сессии остаётся first-party (`__Host-fs_session`, `SameSite=Strict`), CORS для REST не нужен. Серверные компоненты Next.js ходят на Render по `BACKEND_INTERNAL_URL` (публичный HTTPS-адрес Render).
- **WebSocket идёт напрямую на Render.** Origin другой, поэтому cookie `SameSite=Strict` в рукопожатие не попадёт. Решение: перед подключением клиент получает **одноразовый короткоживущий билет** через `/api/realtime/ticket` (same-origin, по cookie) и передаёт его в `auth` рукопожатия Socket.IO. Origin проверяется по allowlist. Тот же механизм подходит и для локального варианта — открытый вопрос Ж. Табло подключается по своему токену (§6.6) и в билете не нуждается.
- **Прокси Render.** TLS завершается на платформе, приложение получает `X-Forwarded-*`. Нужен `trust proxy` в Express: от него зависят IP в аудите и ограничение частоты. Включается **только** при `DEPLOY_TARGET=cloud` — в LAN доверять этим заголовкам нельзя.
- **Один экземпляр backend.** Рассылка realtime идёт внутри процесса (§2), поэтому на Render — ровно один инстанс, без автомасштабирования. Несколько инстансов потребуют адаптера Socket.IO (Redis и т. п.) — отдельное решение.
- **Таймеры после перезапуска.** Render перезапускает сервис при деплое, а на бесплатном тарифе ещё и усыпляет его при простое. Таймеры восстанавливаются из БД (§6.5), но живой поединок в облаке во время деплоя прервётся. Выбор тарифа — открытый вопрос И.
- **Миграции** выполняются отдельной командой перед запуском новой версии (pre-deploy-команда Render или ручной запуск). Приложение не стартует, если миграции не применены (DATABASE.md §6).
- **Соединение с БД** — только по TLS (`sslmode=require` или строже).
- **Монорепозиторий.** Vercel собирает `frontend/`, Render — `backend/` (root directory сервиса). Когда появится `packages/contracts` (этап 2), сборку на обеих платформах нужно запускать с учётом npm workspaces. Это проверяется при первом деплое.
- **Секреты** (`DATABASE_URL`, ключи сессий, `client_secret` Google) задаются в переменных окружения Vercel/Render и в репозиторий не попадают. Значения облака и локального сервера разные.
- **Демо-данные** на публичном стенде допустимы только с пометкой «демонстрационные» (ТЗ §10, §20).

### 9.3. `HOST` и `PORT`

Реализация — **этап 2** (модуль `config`). Сейчас `backend/src/main.ts` слушает `process.env.PORT ?? 3000` **на всех интерфейсах**, а порт по умолчанию совпадает с портом Next.js. На этапе 2 это исправляется.

| Переменная | Локальная разработка | Локальный сервер турнира | Облако: Render (backend) | Облако: Vercel (frontend) |
|---|---|---|---|---|
| backend `HOST` | `127.0.0.1` (умолчание) | Явно: LAN-адрес сервера, либо `127.0.0.1`, если впереди обратный прокси (§11.2 Б) | `0.0.0.0` — Render требует слушать все интерфейсы контейнера, наружу доступ даёт только его прокси | — |
| backend `PORT` | `3001` (умолчание) | `3001` или по конфигурации | Значение `PORT` от Render, не задаётся вручную | — |
| frontend | `next dev` (порт 3000) | `next start -H <адрес> -p 3000` | — | Управляет Vercel |
| `BACKEND_INTERNAL_URL` | `http://127.0.0.1:3001` | `http://127.0.0.1:3001` | — | `https://<сервис>.onrender.com` или свой домен |
| `PUBLIC_ORIGIN` | `http://localhost:3000` | `https://<имя сервера>` | Домен Vercel (для Origin allowlist) | Домен Vercel |

Правила:
- Умолчание `HOST` — `127.0.0.1`. Значение `0.0.0.0` допускается только явным указанием. При `DEPLOY_TARGET=local` backend выводит предупреждение, если `HOST=0.0.0.0`.
- `PORT` — целое число 1–65535, проверяется zod-схемой конфигурации. Невалидное значение → отказ старта, без молчаливого возврата к умолчанию.

### 11.3. Принятые по умолчанию решения по ТЗ

## 17. Входы по ролям, саморегистрация организаторов, PWA (2026-10-17)

**Маршруты.** `/` — публичная стартовая страница с тремя входами. `/dashboard` — обзор (раньше был на `/`). `/judge` — вход судьи и список назначенных поединков. `/display` — открыть табло по ссылке. `/display/<token>` — само табло. `proxy.ts` пропускает без сессии `/`, `/login`, `/judge`, `/display` и `/display/*`, остальное оптимистично перенаправляет на `/login`. Права проверяет backend.

**Саморегистрация организатора** (`POST /api/auth/register`; `GET /api/auth/options` сообщает, включена ли она):
- включается `ALLOW_REGISTRATION`; по умолчанию включена в `dev-http` и выключена в `production`;
- новый пользователь получает только системную роль `organizer_self` с правами `tournament.create` и `athlete.create` (миграция `0003`);
- создавая турнир, он получает роль `organizer` **в пределах этого турнира**. Чужие турниры, матчи, табло и спортсмены ему не видны: `visibleTournamentIds` раскрывает все турниры только при системных `tournament.manage`, `display.operate` или `audit.read`;
- спортсмены: колонка `athletes.created_by`. Без системного `athlete.manage` пользователь видит и меняет только своих спортсменов и тех, кто зарегистрирован в доступных ему турнирах;
- частота регистраций ограничена (5 за 5 минут с одного IP), каждая регистрация пишется в аудит.

**Судьи.** Права судьи нельзя получить самостоятельно. Организатор турнира создаёт учётную запись судьи **в пределах турнира** (`POST /api/tournaments/:id/judges`). Список допустимых судей (`GET /api/tournaments/:id/officials`) и проверка при назначении на поединок разрешают судей этого турнира, а системных судей — только организатору с системными правами.

**`/auth/me` → `capabilities`** (`organizer`, `judge`, `displays`) — подсказка интерфейсу, какие входы показать. Это не авторизация.

**PWA.** `app/manifest.ts` (`standalone`, иконки 192/512 и maskable 512 из `scripts/generate-icons.mjs`), `public/sw.js`. Service worker регистрируется только в production-сборке и только в secure context (HTTPS или `localhost`) и кэширует **только** `/_next/static/*`, `/icons/*` и `/offline.html`. HTML-страницы, `/api/*` и WebSocket всегда идут в сеть; без сервера показывается заглушка «нет связи». Полной офлайн-работы нет. Предложение установки (`beforeinstallprompt` в Chromium, инструкция для iOS Safari) скрываемо и запоминается в `localStorage`. По HTTP через LAN-адрес браузеры установку не предлагают (§9.1).

**Исправлено:** аутентификация WebSocket `/realtime` перенесена из асинхронного `handleConnection` в middleware пространства имён. На медленной БД первое сообщение клиента обгоняло проверку билета, и подписка падала с внутренней ошибкой.

## 18. Проверка демо и замеры (2026-10-17)

Проверки выполнены на временном локальном кластере PostgreSQL 18 (`127.0.0.1:54329`, отдельные базы `fightscore_test` и `fightscore_demo`). В Supabase выполнялось только чтение.

**Задержка.** Сервер БД выполняет любой «горячий» запрос приложения быстрее 0,5 мс (`EXPLAIN ANALYZE`, одинаково локально и в Supabase). Медленных запросов нет. Остальное — сеть:

|---|---|---|
| Обращение к БД (`SELECT 1`) | 0,3 мс | ~320 мс; новое TLS-соединение ~4,4 с |
| Backend, GET-эндпоинты | 5–18 мс | 480–980 мс (было 470–1240 мс до сокращения обращений) |
| Вход (scrypt + сессия) | ~60–250 мс | ~2,3 с (было 3,3 с) |
| Команда судьи → подтверждение / → табло | 6–29 мс / 11–39 мс | не измерялось (команды изменили бы демо-данные); оценка: 2 обращения → ~0,6 с, табло ~0,9 с |
| Frontend TTFB страниц | 11–71 мс | — |
| JS стартовой страницы | 597 КБ (184 КБ gzip) | — |

Сокращено число последовательных обращений к БД: проверка доступа к поединку и список видимых турниров — по одному запросу; вход — один атомарный оператор; данные профиля читаются параллельно.

**Исправлено по итогам проверок:**
- при 10+ одновременных начислениях одна команда могла получить `409 CONFLICT` после исчерпания оптимистичных попыток. Теперь после двух проигранных гонок накопительная команда выполняется под блокировкой строки (`SELECT … FOR UPDATE`). e2e: 25 одновременных команд, ни одна не потеряна;
- e2e ожидал старое поведение WebSocket (`disconnect`); сокет без билета теперь отклоняется на рукопожатии (`connect_error: UNAUTHENTICATED`);
- табло до старта показывало `0:00`, теперь показывает длительность периода из профиля;
- код страны дублировался (эмодзи-флаг Windows рисует буквами), остался значок ISO-кода;
- `next start` слушал все интерфейсы; скрипт `start` теперь слушает `127.0.0.1` (LAN — `next start -H <адрес>`).

**PWA:** Chromium (DevTools `Page.getInstallabilityErrors`) не нашёл ошибок установки на `localhost`, `beforeinstallprompt` срабатывает. Установка по HTTPS в LAN не проверена: нужен доверенный сертификат (§9.1, вопрос Б).

**Записи `zz-test` в Supabase:** 3 пользователя, на них ссылаются 6 строк `audit_log` (append-only, FK). Удаление невозможно без нарушения журнала. По решению владельца (2026-10-17) пользователи деактивированы (`is_active = false`, действующих сессий 0), тестовый турнир архивирован. `audit_log` не изменялся: строк по-прежнему 6, новых записей нет.

## 19. Интерфейс: дизайн-система, темы, профили правил (2026-10-18)

**Темы и предпочтения.** Цвета заданы токенами CSS (`frontend/src/app/globals.scss`): тёмная тема по умолчанию (ТЗ §14) и светлая. Токены переключаются атрибутами на `<html>`: `data-theme` (`dark` | `light`), `data-bg` (фон), `data-density` (плотность), `data-motion` (анимация). Выбор хранится в `localStorage` этого браузера (`lib/preferences.tsx`): это локальная настройка устройства, на сервер она не отправляется, синхронизации между устройствами нет. Inline-скрипт в `<head>` корневого layout применяет сохранённые атрибуты до первой отрисовки (руководство Next.js «preventing flash before hydration»), поэтому тема не мигает. `<html>` помечен `suppressHydrationWarning`. Вариант «Как в системе» следует `prefers-color-scheme` и меняется вместе с ОС. Табло для ТВ (`/display/[token]`) всегда тёмное: атрибут `data-theme="dark"` стоит на его корне.

**Фоны.** Только CSS-градиенты и одна локальная SVG-текстура (`public/backgrounds/octagon.svg`, цвет задаётся через `mask`). Внешних изображений нет. Фон лежит на слое `body::before`, карточки и таблицы непрозрачны, поэтому контраст текста от фона не зависит. Загрузка собственного фона не реализована: нужно хранилище и проверка файлов, а `localStorage` для изображений ненадёжен.

**Кликабельные карточки и строки.** `ui/LinkCard` и `ui/Table` (`LinkRow` + `RowLink`): в карточке или строке ровно одна настоящая ссылка, её `::after` растянут на всю площадь. Клавиатура: Tab до ссылки, Enter. Фокус подсвечивает всю карточку (`:has(:focus-visible)`). Кнопки и ссылки действий лежат выше этого слоя (`z-index`) и работают сами по себе. Обёртка таблицы позиционирована (`position: relative`), чтобы скрытые подписи для экранных читалок не расширяли страницу на телефоне.

**Профили правил: права (миграция `0004_rule_profile_editing.sql`).**
- `rules.manage` выдано системной роли `organizer`: создание общих (`visibility = shared`) неофициальных профилей и управление любыми неофициальными профилями.
- Новое право `rules.create` выдано `organizer_self`: создание личных (`private`) профилей. Они видны автору и держателям `rules.manage`, на чужие профили права изменения нет.
- `rules.approve` (только `owner`) по-прежнему нужен, чтобы утвердить официальный регламент (`is_demo = false`). Без источника (`source_title`, `source_edition`) утверждение невозможно: это проверяют CHECK в БД и API.

**Жизненный цикл версии.** Черновик меняется и удаляется. Публикация переводит его в `approved`, после чего триггер `rule_version_guard` запрещает любые изменения. «Изменить» опубликованную версию значит создать новую версию-черновик (не больше одного черновика на профиль). Архивирование версии (`approved → archived`) и профиля (`archived_at`) запрещает выбирать их для новых поединков, а поединки, уже связанные с версией, сохраняют её. Копия профиля всегда становится новым неофициальным черновиком. API проверяет, что у главного судьи есть действия `timer`, `end` и `confirm`, без которых движок не может начать и завершить поединок. Это эксплуатационное требование, а не спортивное правило.

**Ограничения.** Профиль правил назначается поединку (при создании или подготовке), а не турниру: в модели нет правил по умолчанию для турнира, и такого поля не добавлялось. Сеток (брекетов) и категорий в модели нет, интерфейс их не показывает. Смена имени и пароля в «Настройках» идёт через новые `PUT /api/auth/me` и `POST /api/auth/password`. Смена пароля завершает остальные сеансы пользователя.

## 20. Редизайн интерфейса и знакомство с продуктом (2026-10-18)

**Дизайн-система.** Направление — «тёмно-синий спортивный SaaS» с синим акцентом и дозированными градиентами. Всё задаётся токенами в `globals.scss` (поверхности, границы, тени `--fs-shadow*`, градиенты `--fs-primary-grad`/`--fs-brand-grad`, шкала текста `--fs-text-*`/`--fs-title*`, высота полей `--fs-control-h`, длительности и кривые анимаций `--fs-dur*`, `--fs-ease*`) и в общих компонентах `components/ui`, поэтому изменения расходятся по всем страницам без правки каждой. Обе темы сохранены. Новых зависимостей нет: анимации на CSS, шрифты системные, логотип и иллюстрации нарисованы SVG/CSS (интернет не нужен).

**Поля ввода.** Минимальная высота 44 px (38 px в компактной плотности), горизонтальный отступ 0.9rem, подписи обычным регистром, ошибка с иконкой и `aria-describedby`. `Field` передаёт в render-функцию второй аргумент `describedBy`; старые вызовы с одним аргументом работают как прежде. Пароль — `ui/Form/PasswordInput` с кнопкой «показать/скрыть».

**Анимации.** Только `transform` и `opacity`: появление страниц (`.main > *` в каркасе), диалоги (`@starting-style`, плавное закрытие), меню аккаунта, мобильное меню (выезд без `display: none`), уход toast, подчёркивание вкладок, раскрытие секций стартовой страницы при прокрутке (`animation-timeline: view()`, только где поддерживается, без JS-обработчиков scroll). Настройка «Анимация» и `prefers-reduced-motion` отключают всё через существующие правила в `globals.scss` (добавлен сброс `animation-delay`).

**Знакомство (onboarding).** Отдельного поля в БД и миграции нет, потому что состояние выводится из серверных данных и одинаково на всех устройствах:
- организатор без турниров видит на «Обзоре» приветствие (`widgets/Welcome`) с одним действием «Создать первый турнир»; подробно описан только первый шаг, остальные показаны как то, что появится внутри турнира. После первого турнира приветствие исчезает само;
- «Следующий шаг» на «Обзоре» вычисляется по счётчикам `GET /tournaments` (участники, поединки, статус) ближайшего незавершённого турнира;
- на странице турнира чек-лист подготовки показывает прогресс и выделяет текущий шаг.
Короткие контекстные подсказки (`ui/Tip`) на разделах можно закрыть. Закрытие хранится в `localStorage` (`lib/onboarding.ts`): это удобство отображения, как тема, а не данные пользователя; если его потерять, пользователь просто снова увидит подсказку. Вернуть все подсказки можно из меню аккаунта. Подсказки и приветствие не влияют на права и не считаются признаком входа.

**Исправления по ходу.** Уникальный `id` заголовка в `ConfirmDialog` (на странице турнира два диалога ссылались на один `id`); кнопки нарушений в судейской панели переносят текст вместо наложения; у кнопки меню аккаунта есть доступное имя; на странице поединка внутренний счётчик изменений подписан «Изменений состояния» и отделён от «версии правил».

**Возврат из архива (2026-10-19).** `POST /api/tournaments/:id/unarchive` (право `tournament.manage`, запись `tournament.unarchive` в журнале) снимает `archived_at`; данные турнира архивирование не меняет, миграция не нужна. На странице турнира организатор может также создать нового спортсмена прямо во вкладке «Участники»: существующие `POST /athletes` и `POST /tournaments/:id/athletes` вызываются по очереди.

**Архив только для чтения (2026-10-19).** Единое правило `AccessService.requireTournamentEdit` (право `tournament.manage` + турнир не в архиве, иначе `409 CONFLICT`) стоит на всех изменяющих операциях турнира: правка турнира, регистрация и снятие участников, создание судей, создание поединка, состав и судьи поединка. Судейские команды (`POST /matches/:id/commands`) в архивном турнире отклоняются; системное истечение таймера разрешено, чтобы не оставить период «висящим». Чтение, архивирование и `unarchive` не затронуты.

**Массовая регистрация.** `POST /api/tournaments/:id/athletes/bulk` с `{ athleteIds: uuid[] }` (1–200, без повторов). Каждый спортсмен проверяется отдельно: существует, не в архиве, виден пользователю по тому же правилу, что `GET /athletes` (невидимый отвечает как `not_found`, чтобы не раскрывать чужую базу), ещё не зарегистрирован. Подходящие вставляются одной транзакцией с `ON CONFLICT DO NOTHING` под блокировкой турнира; ответ `{ registered, skipped: [{ athleteId, reason }] }`. Регистрационный номер задаётся при выборе одного спортсмена через прежний `POST /tournaments/:id/athletes`.

**Архивация и регистрация (2026-10-20).** Архивирование отклоняется (`409 CONFLICT`, `details.activeMatches`), пока в турнире есть поединки `live` или `awaiting_confirmation`; проверка идёт после блокировки строки турнира и `match_states` его поединков (тот же порядок, что у судейской команды под блокировкой). Одиночная и массовая регистрация используют общий `registerEntries`: одинаковые проверки существования, видимости и повтора; одиночный ответ прежний (`{ id }`), недоступный спортсмен — `404`, повтор — `409`. Состав поединка теперь проверяет, что дисциплина относится к турниру (раньше это проверялось только при правке турнира).

## 21. Турнирные сетки и правила завершённого турнира (2026-10-20)

**Формат.** Реализована одна законченная система — олимпийская (single elimination), одна сетка на дисциплину турнира. Категорий (весов, возрастов) в модели нет, поэтому сетка строится по дисциплине; групп, «утешительных» поединков и двойного выбывания нет.

**Хранение (миграция `0005_brackets.sql`, только добавления).** Таблица `brackets` (дисциплина, версия правил, размер 2–64, `UNIQUE (tournament_id, discipline_id)` — повторное создание невозможно). Поединки сетки — обычные `matches` с позицией `bracket_id`, `bracket_round`, `bracket_slot` (`UNIQUE` на позицию) и `bracket_advanced_side` (кто прошёл дальше; задаётся один раз). Победитель позиции (r, s) переходит в (r + 1, ⌊s/2⌋): красный угол при чётном s, синий при нечётном. Раскладка — `matches/bracket.ts` (стандартный посев, проходы без боя получают сильнейшие).

**Создание** `POST /tournaments/:id/brackets { disciplineId, ruleVersionId, entryIds }` (участники в порядке посева): сразу создаются все поединки всех кругов через тот же путь, что и одиночный поединок (`insertMatch` + `applySetup`: проверки версии правил и регистрации). Пары первого круга без соперника не создаются — спортсмен садится во второй круг. Состав поединков сетки потом не меняется: `PUT /matches/:id/setup` отвечает 409.

**Продвижение.** В том же SQL-запросе, что фиксирует подтверждённый результат (`ScoringService` `WRITE_SQL`), победитель записывается участником следующего поединка, если тот ещё «Подготовка», и ставится `bracket_advanced_side`. Подтверждённый результат неизменяем, поэтому противоречивых продвижений нет. Если поединок отменён или завершён без победителя, организатор назначает проход: `POST /matches/:id/walkover { side }` (один раз, только при отсутствии победителя, только пока следующий поединок не начат; запись `bracket.walkover` в журнале). Просмотр: `GET /tournaments/:id/brackets`, вкладка «Сетка» на странице турнира.

**Завершённый турнир.** `AccessService.requireMatchesOpen`: в турнире со статусом «Завершён» нельзя создать поединок или сетку, изменить состав поединка, назначить судей и проход (409). Чтение, результаты и смена статуса турнира не затронуты.

**Гонка архивации и судейства — устранена.** Запись судейской команды (`WRITE_SQL`) обновляет состояние только вместе с `FOR KEY SHARE` на строке турнира при `archived_at IS NULL`; архивация берёт `FOR UPDATE` на ту же строку и проверяет активные поединки. Конфликтующие блокировки сериализуют операции: команда, начатая до архивации, либо завершается раньше (и архивация видит активный поединок), либо ждёт и после неё не пишет (0 строк → конфликт версии, повтор видит архив). Архивация больше не блокирует `match_states`, поэтому цикла ожидания с судейской командой нет. `KEY SHARE` не конфликтует с обычными `UPDATE tournaments`.

**Жизненный цикл сетки (2026-10-20).**
- *Обновление следующего поединка.* `WRITE_SQL` возвращает `advanced_to` — поединок, в который в той же транзакции посажен победитель. После фиксации `ScoringService.notifyChanged` отправляет его в существующий поток `changes`: шлюз рассылает снимок судьям этого поединка и публичную проекцию (`publicView`) табло. Клиент принимает снимок той же версии (`>=`), поэтому новый участник появляется без перезагрузки. Ручной проход уведомляет так же. Вкладка «Сетка» не подписана на сокет и обновляется раз в 10 с, пока страница видна и в сетке есть поединки «Готов», «Идёт» или «Ждёт подтверждения».
- *Отмена.* Поединок сетки можно отменить, только когда известны оба соперника (иначе `409`). Поэтому победитель никогда не продвигается в отменённый поединок; для отменённой известной пары организатор назначает проход вручную.
- *Блокировки.* Создание поединка и сетки берёт `FOR UPDATE` на строку турнира и только затем проверяет архив и статус; ручной проход — `FOR SHARE`. Архивация и смена статуса турнира ждут этих транзакций или они видят результат. Судейская команда держит `match_states` и берёт на турнир лишь `KEY SHARE`, а перечисленные операции не блокируют существующие `match_states`, поэтому цикла ожидания нет.
