# FightScore — полное техническое задание проекта

- **Версия:** 1.0
- **Статус:** первоначальная спецификация
- **Тип проекта:** веб-платформа управления соревнованиями по единоборствам с возможностью установки на устройства и автономной работы в локальной сети.

## 1. Концепция проекта

FightScore — профессиональная система для организации и проведения соревнований по единоборствам.

Платформа объединяет управление турнирами, спортсменами, судьями, поединками, счётом, временем и результатами. Она должна предоставлять отдельный интерфейс организатора, судейскую панель и полноэкранное табло для телевизора.

Основной сценарий: главный судья управляет поединком на ноутбуке, а зрители одновременно видят актуальный счёт и таймер на большом экране.

Основные принципы:

- единый источник достоверного состояния поединка;
- обновление данных в реальном времени;
- разграничение прав пользователей;
- поддержка нескольких дисциплин и версий спортивных регламентов;
- работа в локальной сети без внешнего интернета;
- надёжное сохранение результатов и истории действий;
- расширяемая архитектура без необходимости переписывать ядро при добавлении новых дисциплин.

Рабочее название FightScore является временным и должно быть легко заменяемым.

## 2. Основные цели

1. Создавать и управлять турнирами.
2. Вести базу спортсменов, стран, клубов и категорий.
3. Создавать поединки и назначать судей.
4. Управлять счётом, таймером, предупреждениями и штрафами согласно выбранному регламенту.
5. Отображать состояние поединка на отдельном телевизионном табло.
6. Сохранять историю действий и официальные результаты.
7. Поддерживать работу нескольких устройств в одной локальной сети.
8. Предоставлять возможность установки приложения на совместимые устройства.
9. Поддерживать вход через локальные учётные записи и Google OAuth при наличии интернета.
10. Обеспечить дальнейшее расширение платформы новыми дисциплинами, турнирами и функциями.

## 5. Архитектура

Предпочтительна архитектура модульного монолита.

Компоненты:

1. Next.js — пользовательские интерфейсы.
2. NestJS — бизнес-логика, авторизация, REST API и WebSocket Gateway.
3. PostgreSQL — постоянное хранение данных.
4. Сервис синхронизации — распространение подтверждённых изменений.
5. Сервис таймера — расчёт времени на основании серверных временных меток.
6. Механизм правил — проверка спортивных действий согласно активному профилю.
7. Журнал аудита — история значимых операций.
8. Локальный сервер — запуск системы в сети организатора без зависимости от внешнего интернета.

Сервер является единственным источником достоверного состояния поединка. Клиент не может самостоятельно объявлять спортивное действие подтверждённым.

Frontend, backend и база данных должны иметь чёткие границы ответственности. Бизнес-правила нельзя реализовывать только в React-компонентах.

## 6. Локальная работа без интернета

Это обязательное требование проекта.

Предусмотреть режим, при котором сервер и PostgreSQL запускаются на компьютере организатора или выделенном компьютере в локальной сети.

Ноутбук судьи, устройство оператора и телевизионный компьютер подключаются к серверу через локальную сеть.

Требования:

- отсутствие зависимости от внешнего API для проведения локального поединка;
- локальная авторизация;
- загрузка локально доступных интерфейсов, шрифтов, иконок и ресурсов;
- сохранение результатов в локальной PostgreSQL;
- синхронизация устройств внутри локальной сети;
- возможность восстановления после перезапуска;
- отображение состояния сетевого соединения;
- резервное копирование и восстановление;
- документированная процедура установки и обновления сервера.

PWA используется для установки интерфейса, но не считается заменой локальному backend.

Google OAuth доступен только при наличии интернета. При отсутствии подключения должны оставаться доступными локальные аккаунты.

Если интернет отсутствует, но локальная сеть работает, соревнование должно продолжаться. Если локальный сервер или локальная сеть недоступны, интерфейс обязан явно сообщать об ошибке и не выдавать устаревшие данные за актуальные.

Не обещать поддержку полноценной работы без локальной сети или сервера, если отдельная архитектура для этого не реализована.

- Доступ к назначенным поединкам.

- Доступ только к назначенным поединкам.
- Выполнение разрешённых действий.
- Возможность подтверждать отдельные решения, если это предусмотрено конфигурацией соревнования.

## 9. Модель данных

Предусмотреть следующие сущности:

- `User` — пользователь.
- `Role` — системная роль.
- `UserRoleAssignment` — назначение роли с областью действия.
- `Tournament` — турнир.
- `Country` — страна.
- `Club` — клуб.
- `Athlete` — спортсмен.
- `Discipline` — дисциплина.
- `Category` — категория.
- `RuleProfile` — профиль правил.
- `RuleProfileVersion` — неизменяемая версия утверждённого профиля.
- `TournamentAthlete` — участие спортсмена в турнире.
- `Match` — поединок.
- `MatchParticipant` — участник поединка и его сторона.
- `MatchOfficial` — назначенный судья и его разрешения.
- `MatchState` — актуальное состояние поединка.
- `MatchEvent` — журнал подтверждённых событий.
- `MatchResult` — итоговый результат.
- `Display` — конфигурация публичного табло.
- `AuditLog` — аудит административных действий.
- `Session` или `RefreshToken` — управление сессиями, если это требуется выбранной схемой авторизации.

Требования:

- единый тип идентификаторов;
- внешние ключи;
- необходимые уникальные ограничения;
- корректные правила удаления;
- временные метки;
- индексы по часто используемым фильтрам;
- транзакции для согласованных изменений;
- версия состояния для защиты от конфликтующих обновлений.

Утверждённые версии правил и подтверждённые результаты должны сохранять историческую целостность.

## 10. Правила спортивных дисциплин

Поддержать разные дисциплины, например:

- MMA;
- Sambo;
- Brazilian Jiu-Jitsu;
- Wrestling;
- Boxing;
- другие дисциплины в будущем.

Названия в списке являются примерами. Реализация конкретной дисциплины допускается только после определения соответствующего регламента.

Не придумывать и не зашивать в общий код неподтверждённые спортивные правила.

Профиль правил должен описывать:

- источник и версию регламента;
- разрешённые действия начисления и снятия баллов;
- настройки времени и периодов;
- типы предупреждений и штрафов;
- разрешённые способы завершения поединка;
- проверки корректности действий;
- ограничения для судей;
- дату вступления в силу;
- статус и подтверждение ответственного лица.

Неизменяемая версия профиля привязывается к поединку. Обновление правил не должно незаметно менять логику уже созданных или завершённых поединков.

Механизм правил должен быть расширяемым. Нельзя строить всю спортивную логику на одном универсальном наборе кнопок.

До получения официальных документов можно реализовать интерфейс конфигурации, валидацию и тестовые профили, явно помеченные как демонстрационные.

## 11. Логика поединка

Предусмотреть контролируемые состояния, например:

- подготовлен;
- ожидает начала;
- идёт;
- пауза;
- ожидает подтверждения результата;
- завершён;
- отменён.

Окончательный перечень и допустимые переходы определяются бизнес-правилами.

Все переходы проверяются сервером. Клиент не может самостоятельно присвоить поединку произвольный статус.

Начисление баллов, снятие баллов, запись предупреждения, изменение времени и завершение поединка должны быть отдельными проверяемыми операциями.

Каждая подтверждённая операция сохраняется в журнале.

Исправления должны создавать новые записи аудита, а не бесследно стирать историю.

## 12. Таймер

Таймер должен использовать серверные временные метки, а не только клиентский интервал JavaScript.

Хранить:

- статус;
- оставшееся время;
- время последнего запуска;
- версию состояния;
- историю корректировок.

При запуске фиксируется серверное время. При паузе вычисляется и сохраняется оставшееся время. Клиенты визуально отображают отсчёт, периодически сверяясь с сервером.

После перезагрузки сервер восстанавливает таймер по сохранённому состоянию.

Не допускать двойного запуска, потери изменений или произвольного отрицательного времени. Допустимые значения и переходы должны определяться профилем правил.

Для официального использования необходимы тесты точности, восстановления и сетевых задержек. Нельзя гарантировать идеальную точность без измерений и проверки реального оборудования.

## 13. WebSocket-синхронизация

WebSockets используются для подписки на поединок и доставки подтверждённых изменений.

Предусмотреть команды и события для:

- подключения и авторизации;
- подписки на разрешённый поединок;
- получения актуального состояния;
- изменения счёта;
- управления таймером;
- записи предупреждений;
- завершения поединка;
- повторной синхронизации;
- сообщения об ошибках.

Каждая команда изменения должна проходить серверную авторизацию, валидацию и проверку бизнес-правил.

Для защиты от повторной отправки предусмотреть идентификаторы команд. Для параллельных изменений — транзакции и проверку версии состояния.

После переподключения клиент получает актуальное подтверждённое состояние и версию, а не просто продолжает отображать старые данные.

## 14. Дизайн-система

Стиль: премиальная международная спортивная платформа.

Основные требования:

- глубокий тёмно-синий фон;
- красная и синяя стороны поединка;
- крупная спортивная типографика;
- высококонтрастное телевизионное табло;
- продуманные состояния загрузки, ошибки, пустые списки и отсутствие связи;
- адаптивная сетка;
- доступность клавиатурной навигации;
- единые компоненты кнопок, полей, карточек, таблиц, диалогов и уведомлений;
- минимальное количество отвлекающих элементов во время поединка.

Не копировать готовый продукт или чужой фирменный стиль. Создать самостоятельную визуальную систему.

Дизайн судейской панели должен быть ориентирован на скорость и предотвращение ошибок. Публичное табло должно иметь отдельную компоновку, рассчитанную на большой экран.

## 15. Безопасность

Обязательные требования:

- стойкое хеширование паролей;
- безопасное управление сессиями;
- проверка прав на сервере;
- валидация всех входных данных;
- защита от повторных команд;
- ограничение частоты запросов;
- защита от CSRF и XSS согласно архитектуре авторизации;
- отсутствие секретов в клиентском коде;
- безопасное хранение ключей и конфигурации;
- аудит критичных операций;
- отдельный доступ к публичному табло;
- запрет доступа между чужими турнирами;
- резервное копирование;
- документированное восстановление;
- контролируемые миграции базы данных.

В локальном режиме сервер должен быть доступен только на необходимых сетевых интерфейсах. Нельзя открывать его всему интернету по умолчанию.

Публичный идентификатор табло не должен предоставлять права управления поединком.

## 16. Локальное развёртывание

Подготовить документированную процедуру:

1. Установка необходимых зависимостей или подготовка контейнеров.
2. Настройка окружения.
3. Запуск PostgreSQL.
4. Выполнение миграций.
5. Создание первого администратора безопасным способом.
6. Запуск backend и frontend.
7. Подключение ноутбука и телевизора к локальной сети.
8. Проверка доступности сервера с каждого устройства.
9. Проверка работы без интернета.
10. Создание резервной копии и проверка восстановления.

Не помещать реальные пароли в репозиторий и не использовать демонстрационные секреты в производственной конфигурации.

## 17. Тестирование

Обязательные категории:

- unit-тесты бизнес-логики;
- тесты профилей правил;
- тесты таймера;
- интеграционные тесты API и PostgreSQL;
- тесты авторизации и разрешений;
- тесты WebSocket-событий;
- тесты параллельных изменений;
- end-to-end тесты полного сценария;
- тесты восстановления после перезапуска;
- тесты работы при потере и восстановлении соединения;
- тесты локального режима без интернета;
- тесты адаптивности и читаемости табло.

Ключевой сценарий:

> создать турнир → добавить спортсменов → создать поединок → назначить судей → выбрать профиль правил → запустить поединок → изменить счёт → поставить таймер на паузу → возобновить → завершить поединок → подтвердить результат → проверить журнал → перезапустить сервер → убедиться, что подтверждённые данные сохранены.

## 18. Критерии готовности MVP

Первая версия не считается готовой, пока:

- можно создать турнир и добавить спортсменов;
- можно создать поединок и назначить судей;
- сервер корректно проверяет права;
- выбранный профиль правил определяет разрешённые операции;
- счёт и таймер синхронизируются с публичным табло;
- параллельные изменения не приводят к потере подтверждённых данных;
- действия фиксируются в журнале;
- результат сохраняется;
- приложение работает в локальной сети без интернета;
- после перезапуска восстанавливаются подтверждённые данные;
- зритель не может управлять поединком;
- тесты проходят, а инструкция локального развёртывания проверена.

## 19. Этапы реализации

- **Этап 1.** Аудит существующего репозитория и фиксация архитектурных решений.
- **Этап 2.** Структура проекта, база данных, миграции и авторизация.
- **Этап 3.** Дизайн-система, сайдбар и основные страницы.
- **Этап 4.** Спортсмены, страны, клубы, турниры, категории и поединки.
- **Этап 5.** Роли, назначения судей и профили правил.
- **Этап 6.** Судейская панель, таймер, счёт и журнал событий.
- **Этап 7.** WebSocket-синхронизация и публичное табло.
- **Этап 8.** Локальный режим, PWA, восстановление и резервное копирование.
- **Этап 9.** Полное тестирование и пилотное соревнование.

Каждый этап должен иметь отдельный проверяемый результат. Следующий этап начинается после проверки предыдущего.

## 20. Требования к процессу разработки

- Сначала изучать существующий репозиторий.
- Не переписывать рабочие части без причины.
- Не создавать лишние абстракции и зависимости.
- Не дублировать бизнес-логику между frontend и backend.
- Не хранить состояние поединка только в браузере.
- Не использовать фиктивные правила как реальные.
- Не считать моковые данные готовой интеграцией.
- Не заявлять о прохождении тестов без их фактического запуска.
- Не скрывать ошибки типизации, линтера или сборки.
- Не удалять существующие функции без согласования.
- Не выполнять массовые изменения без предварительного плана.
- После каждого этапа проверять сборку и относящиеся к нему тесты.
- Документировать принятые архитектурные решения.
- Экономно использовать контекст и токены AI-инструментов.

## 21. Итоговый принцип

FightScore должен стать надёжной системой управления соревнованиями, а не просто красивым счётчиком.

Приоритеты разработки:

1. Корректность спортивных данных.
2. Надёжность счёта и таймера.
3. Безопасность и разграничение прав.
4. Согласованность всех экранов.
5. Работа в локальной сети без интернета.
6. Удобство судей и организаторов.
7. Расширяемость на новые дисциплины и форматы соревнований.

Все спортивные правила должны происходить из проверяемых регламентов. Все архитектурные решения должны быть документированы, а готовность функций подтверждаться тестами.
