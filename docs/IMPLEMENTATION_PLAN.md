# FightScore — план реализации

- **Статус:** черновик этапа 1, ждёт утверждения.
- **Основа:** этапы [PROJECT_SPEC.md §19](PROJECT_SPEC.md#19-этапы-реализации), критерии MVP §18. Решения — в [ARCHITECTURE.md](ARCHITECTURE.md) и [DATABASE.md](DATABASE.md).

## Правила для всех этапов

- Этап завершён, когда **выполнены и проверены** его критерии готовности. Следующий этап начинается после проверки предыдущего (ТЗ §19).
- Перед закрытием этапа: `tsc --noEmit` (оба приложения), линтеры (`eslint` во frontend, `oxlint` в backend), сборка (`next build`, `nest build`) и тесты этапа — **фактически запущены**, вывод приложен к отчёту.
- Новые зависимости — только из списка ARCHITECTURE §10 или с отдельным обоснованием в `docs/adr/`.
- Каждый этап обновляет `DATABASE.md`/`ARCHITECTURE.md`, если решение изменилось. Расхождение кода и документа — дефект.
- Демо-данные и демо-профили всегда помечены как демонстрационные. UI без backend-интеграции не считается готовой функцией.

Интеграционные тесты требуют локальный PostgreSQL (`fightscore_test`). Установка PostgreSQL — предусловие этапа 2.

## Этап 2. Основа: репозиторий, БД, миграции, авторизация

**Состав:**
1. Единый git-репозиторий, корневой `package.json` с npm workspaces, `packages/contracts` (ESM, сборка `tsc`). `.gitignore`, `.env.example`, `engines.node` (LTS).
2. Backend: модуль `config` (zod-проверка env, отказ стартовать с демо-секретами в production), `database` (пул `pg`, `withTransaction`), раннер миграций, скрипт проверки «все миграции применены» при старте.
3. Удаление `@nestjs/observe` (если согласовано), `HOST`/`PORT` из конфигурации, по умолчанию `127.0.0.1`.
4. Миграции: `users`, `user_identities`, `sessions`, `roles`, `role_permissions`, `user_role_assignments`, `audit_log` + триггер append-only + роли БД `fightscore_owner`/`fightscore_app`.
5. Модули Audit, Access, Users, Auth: вход/выход по паролю (scrypt), серверные сессии, `AuthGuard`, `PermissionGuard`, `@RequirePermission`, проверка Origin + заголовок `X-FightScore-Request`, throttling входа.
6. CLI `create-owner`.
7. CI (GitHub Actions или аналог — по наличию remote): typecheck, lint, unit, интеграционные тесты с сервисом PostgreSQL.

**Готово, когда:**
- `migrate` на пустой БД создаёт схему; повторный запуск ничего не делает; изменённый применённый файл даёт ошибку;
- владелец создаётся CLI, входит, получает httpOnly-cookie, выходит; отозванная сессия не работает;
- эндпоинт под `@RequirePermission` возвращает 401 без сессии и 403 без права;
- вход, выход, неудачный вход и создание пользователя пишутся в `audit_log`; `UPDATE audit_log` падает.

**Тесты:** unit (scrypt-хеш, разбор конфигурации, PermissionService); интеграционные на реальной БД (раннер миграций, триггеры, уникальности); e2e (вход/выход/401/403/CSRF-отказ/лимит частоты).

## Этап 3. Дизайн-система, каркас и основные страницы

**Состав:**
1. Решение вопроса 2 (SCSS Modules), дизайн-токены (цвета красной/синей стороны, тёмно-синий фон, типографика, отступы) в CSS-переменных; локальные шрифты `next/font/local`.
2. `components/ui`: кнопка, поле, select, карточка, таблица, бейдж, диалог подтверждения, уведомление, индикатор связи, состояния загрузки/ошибки/пусто.
3. `components/layout`: сайдбар, хедер, футер; отдельные layout для `judge/` и `display/`.
4. `src/lib/api`: серверный клиент (проброс cookie) и клиентский (`/api` + заголовок CSRF), разбор формата ошибок; rewrite `/api/*` в `next.config.ts`; `proxy.ts` с оптимистичным редиректом.
5. Страница входа и обзор (`/`) с реальными данными, доступными на этом этапе (текущий пользователь, его роли). Пустые блоки показывают пустое состояние, а не выдуманные данные.

**Готово, когда:** вход через UI работает с backend; навигация по клавиатуре доходит до всех элементов; страницы читаемы на ширине 375 px и 1920 px; нет обращений к внешним хостам (проверка по вкладке Network при отключённом интернете).

**Тесты:** компонентные тесты ключевых UI-элементов (тестовый стек frontend выбирается здесь: Vitest + Testing Library — обоснование в ADR); e2e входа (Playwright — ADR); `next build` без ошибок.

## Этап 4. Справочники, спортсмены, турниры, категории, поединки

**Состав:**
1. Миграции: `countries` (+ данные ISO 3166-1), `clubs`, `disciplines`, `athletes`, `tournaments`, `tournament_disciplines`, `categories`, `tournament_athletes`. Локальные файлы флагов.
2. Модули Athletes, Disciplines, Tournaments: CRUD + архивирование, оптимистичная блокировка по `updated_at`, фильтры и пагинация, аудит изменений.
3. Миграции `matches`, `match_participants`, `match_states` и модуль Matches (без правил и судей): создание поединка в `prepared` с `rule_profile_version_id = NULL`, стороны red/blue, список с фильтрами. `match_states` создаётся в той же транзакции. Внешний ключ на `tournament_rule_versions` добавляется миграцией этапа 5.
4. Страницы: турниры (список, карточка, участники, категории), спортсмены, страны, клубы, дисциплины.

**Готово, когда:** организатор создаёт турнир, добавляет дисциплину, категорию, спортсменов и регистрирует их; пользователь без прав турнира получает 403 при доступе к нему (ТЗ §15 «запрет доступа между чужими турнирами»); архивированный турнир не попадает в активные.

**Тесты:** интеграционные на ограничения (даты турнира, год/дата рождения, уникальности, категория только в дисциплине турнира); e2e CRUD с проверкой прав по области турнира.

## Этап 5. Роли, судьи, профили правил

**Состав:**
1. Миграции: `rule_profiles`, `rule_profile_versions` + триггер неизменяемости, `tournament_rule_versions`, внешний ключ `matches → tournament_rule_versions`, `match_officials`.
2. `packages/contracts`: zod-схема `definition` профиля правил.
3. Модуль Rules: черновик → утверждение (`rules.approve`) → архив; просмотр различий версий; движок `generic-points@1` — чистые функции без сетевого и БД-кода.
4. **Демо-профиль** для тестов и разработки: `is_demo = true`, все значения явно условные, пометка в UI. Официальные профили создаются только при наличии регламента от владельца.
5. Модуль Officials: назначение главного судьи и судей, права в поединке; управление ролями пользователей в турнире.
6. Выбор версии правил для поединка в `prepared` и переход `prepared → ready` с проверкой полноты (обе стороны, главный судья, утверждённая версия из разрешённых для турнира).
7. Страницы: дисциплины и правила (редактор черновика, утверждение, история версий), поединки (создание, назначение судей), управление пользователями турнира.

**Готово, когда:** утверждённую версию нельзя изменить ни через API, ни прямым SQL (триггер); неdemo-версия без источника не утверждается; поединок привязан к версии, и её архивирование не меняет поединок; судья видит только назначенные поединки.

**Тесты:** unit-тесты схемы `definition` и движка (табличные тесты на демо-профиле); интеграционные на триггеры и права; e2e назначения судей.

## Этап 6. Судейская панель, таймер, счёт, журнал

**Состав:**
1. Миграция `match_events` (append-only), `match_results`.
2. Модуль Scoring: конвейер команд (ARCHITECTURE §6.2), идемпотентность по `commandId`, классификация команд и `VERSION_CONFLICT`, таймер на серверном времени, планировщик истечения и его восстановление при старте, исправления через `event.void` с пересчётом воспроизведением, завершение → `awaiting_confirmation` → подтверждение результата → `match_results`.
3. HTTP-транспорт команд: `POST /api/matches/:id/commands`, `GET /api/matches/:id/state` (WS — этап 7, тот же сервис).
4. Публикация `MatchStateChanged` после коммита (подписчиков пока нет — только тесты).
5. Страница судейской панели на HTTP-транспорте: стороны, счёт, таймер, предупреждения, журнал, подтверждение опасных действий, состояние «отправлено, ждёт сервера».

**Готово, когда:** весь сценарий поединка проходит через API; повтор команды с тем же `commandId` не дублирует событие; две параллельные накопительные команды обе применяются; две параллельные «зависящие от состояния» → одна принята, другая `VERSION_CONFLICT`; `match_states` совпадает со свёрткой журнала; после перезапуска процесса таймер продолжает с верным временем.

**Тесты:** unit таймера (старт/пауза/двойной старт/ноль/корректировка, внедрённые часы); unit движка; интеграционные конкурентности (параллельные транзакции на реальной БД); тест восстановления (остановить и поднять Nest-приложение в тесте, проверить таймер и состояние); e2e сценария поединка по HTTP.

## Этап 7. WebSocket-синхронизация и публичное табло

**Состав:**
1. Установка Socket.IO-пакетов (проверка совместимости с NestJS 12).
2. Модуль Realtime: namespace `/realtime` (сессия + Origin + права на каждую подписку и команду) и `/public` (токен табло, только чтение); протокол ARCHITECTURE §6.6; ping для оценки смещения часов.
3. Миграция `displays` и модуль Displays: CRUD табло, перевыпуск токена, привязка поединка оператором (`display.operate`), публичная проекция состояния.
4. `src/lib/realtime`: подключение, переподключение, `resync` при разрыве версий, очередь неподтверждённых команд, индикатор связи. Судейская панель переходит на WS-транспорт.
5. Страница `/display/[token]`: полноэкранная компоновка, крупный счёт и таймер, плашка потери связи. Обзор показывает статус подключённых табло.
6. Проверка: проксирует ли rewrite Next.js WebSocket upgrade. Результат фиксируется в ADR.

**Готово, когда:** изменение счёта у судьи видно на табло без перезагрузки; табло с чужим или неверным токеном ничего не получает; через `/public` нельзя отправить команду; после обрыва сети клиент получает актуальный снимок, а неподтверждённые команды не теряются и не дублируются.

**Тесты:** интеграционные WS (подключение без сессии → отказ, подписка без прав → отказ, команда через `/public` → отказ, обрыв и переподключение, пропуск версии → resync); e2e «судья + табло» в двух браузерных контекстах; проверка читаемости табло на 1920×1080 и 3840×2160.

## Этап 8. Локальный режим, PWA, резервное копирование

**Состав:**
1. `docs/ops/install.md`, `update.md`, `backup-restore.md` по шагам ТЗ §16.
2. Скрипты `backup`/`restore` (`pg_dump -Fc` / `pg_restore`), обязательная копия перед `migrate` в процедуре обновления.
3. PWA: `app/manifest.ts`, иконки, service worker только для статической оболочки; CSP и заголовки безопасности.
4. Решение по HTTPS в LAN (вопрос 5): локальный центр сертификации или документированное ограничение.
5. Google OAuth (если на этом этапе есть HTTPS и redirect URI): code flow + PKCE, привязка к существующему пользователю, скрытие при отсутствии интернета.
6. Сетевые интерфейсы: backend и frontend слушают только заданный LAN-адрес, PostgreSQL — `localhost`.

**Готово, когда:** установка по документу на чистой машине проходит без отступлений; полный поединок проходит при физически отключённом интернете; резервная копия восстанавливается в чистую БД, и данные совпадают; при остановленном сервере все клиенты явно показывают потерю связи.

**Тесты:** скриптовая проверка backup → restore → сравнение количества строк и контрольных сумм ключевых таблиц; e2e при заблокированном внешнем трафике.

## Этап 9. Полное тестирование и пилот

**Состав:**
1. Сквозной e2e ключевого сценария ТЗ §17 целиком, включая перезапуск сервера.
2. Измерение точности таймера на реальном оборудовании (ноутбук судьи, ТВ-компьютер, роутер организатора): расхождение показаний, задержка доставки. Отчёт в `docs/`.
3. Нагрузочный прогон: несколько одновременных поединков и табло (число — по ожидаемому масштабу пилота).
4. Пилотное соревнование с **официальным** профилем правил, созданным по регламенту, предоставленному владельцем.

**Готово (MVP, ТЗ §18):** все пункты ТЗ §18 подтверждены тестами или протоколом пилота; инструкция развёртывания проверена на отдельной машине; открытые дефекты пилота разобраны.
